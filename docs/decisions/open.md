### `OPEN-3` — the deadline moved, and why that is not a slip

The original deadline was *before the seed generator*, on the expectation that the seed load
would depend on this choice. **It did not.** The loader uses `COPY`, which bypasses
Hibernate entirely and supplies explicit ids, so the generator landed without the question
ever binding. The deadline is re-dated rather than quietly dropped.

**What binds instead is the first entity**, which now exists. `BaseEntity` uses `IDENTITY`,
matching `V1`'s `generated by default as identity`. **That is provisional, it is recorded as
provisional in the source, and this row stays open** — writing `ADR-003` now would violate
this row's own terms, which say the trade is worth measuring rather than assuming. There is
no bulk insert path yet, so there is nothing to measure.

**A hazard to carry into that decision, discovered while loading the seed.** After the
`COPY`, the loader calls `setval` on each table's identity sequence so the next application
insert continues past the loaded rows. If `OPEN-3` later chooses a sequence generator, that
generator must be **the same sequence the loader realigns** — otherwise Hibernate allocates
from a sequence starting at 1 and the first insert collides with a row the seed already
loaded. **That failure appears only against a seeded database and never against an empty
test one**, which is precisely the class of defect this repository exists to collect.
