# 6장 — 인덱스는 쓰이고 있었고, 틀렸습니다

**그럴듯한 인덱스, 균등한 데이터, 그리고 답을 담을 수 없는 질문**

> 대상: 5장을 읽은 사람. `CREATE INDEX` 는 써봤지만 `EXPLAIN` 을 습관적으로 보지는 않는 사람
> 목표: *"인덱스가 쓰이나?"* 라는 질문이 **왜 부족한지**, 그리고 무엇을 대신 물어야 하는지까지
> 선행: 5장 8절(제약이 인덱스이기도 하다). 그 인덱스를 이제 정면으로 봅니다
>
> **감사 2026-08-20** — `R1`~`R9` 및 `R12`~`R19` 와 대조했습니다.
> **`R0`·`R10`·`R11` 은 읽지 않았습니다** — 총괄 기록과 T9(인가·노출·토큰)이고, 이 장의 문장을 반증하는지 미확인.

## 0. 이 장의 한 문장

> **인덱스에 대한 거의 모든 확인이 "쓰이는가"에서 멈추고,
> 이 장의 결함 중 어느 것도 그 질문으로는 잡히지 않습니다.**

앞의 다섯 장은 *"무엇이 잘못됐나"* 를 물었습니다. 이 장은 한 칸 더 갑니다 — **내가 던진 질문이 답을 담을 수 있는 모양이었나.**

여기서 이 저장소는 **재고도 아무것도 못 찾은 적이 두 번** 있고, 두 번 다 이유가 결함이 없어서가 아니었습니다.

## 1. 당신이 이미 알고 있는 것에서 출발

### 1.1 전화번호부

`(성, 이름)` 순으로 정렬된 전화번호부가 있습니다.

- **"김씨를 찾아라"** → 쉽습니다. 김씨 구간으로 바로 내려갑니다.
- **"철수를 찾아라"** → 처음부터 끝까지 훑어야 합니다.

**B-tree 인덱스가 정확히 이렇습니다. 선행 컬럼으로 먼저 정렬됩니다.**

그런데 여기서 한 발 더 갑니다. `(이름, 성)` 으로 정렬된 책에서 **"김철수"** 를 찾으면 어떻게 될까요?

**쓰이긴 합니다.** 철수 구간으로 내려간 다음 거기서 김씨를 훑으면 됩니다. 철수가 몇 명 없으면 빠릅니다.

**그런데 철수가 3만 명이면 무너집니다.** 그리고 이 장의 4절이 그 이야기입니다.

### 1.2 `OFFSET` 은 건너뛰기가 아닙니다

```sql
select * from attempt order by attempted_at desc offset 1000 limit 20;
```

**1000개를 건너뛰는 게 아니라, 1000개를 만들어서 버리고 1001번째에 도달합니다.**

비용이 offset에 **비례해서** 늘어납니다. 7절에서 그 비용을 잽니다 — 그리고 **"그러니 keyset 페이징을 써라"** 라는 널리 옳은 조언이, 이 저장소에서는 값을 못 하는 것도 같이 봅니다.

## 2. 어휘 — 원문 그대로 익히기

| 원문 용어 | 한글 표기 | 한 줄 설명 |
|---|---|---|
| **B-tree** | — | 기본 인덱스 구조. **선행 컬럼으로 먼저 정렬** ⁽¹⁾ |
| **leading column** | 선행 컬럼 | 복합 인덱스의 맨 앞 컬럼. **이 장의 4절 전체** |
| **`EXPLAIN`** | — | 데이터베이스에게 *"어떻게 실행할 거냐"* 고 묻는 것 ⁽²⁾ |
| **Seq Scan** | 순차 스캔 | 테이블을 처음부터 끝까지 읽음 |
| **Index Scan** | 인덱스 스캔 | 인덱스로 내려가서 필요한 것만 |
| **Index Only Scan** | — | **힙을 아예 안 건드림** → 6절 |
| **selectivity** | 선택도 | 조건이 몇 행이나 걸러낼지의 비율 ⁽³⁾ |
| **cardinality** | 카디널리티 | 컬럼이 갖는 서로 다른 값의 개수 → 5절 |
| **`ANALYZE`** | — | 플래너가 쓸 통계를 다시 수집 ⁽³⁾ |
| **skew** | 쏠림 | 한 값이 유독 많은 분포 ⁽³⁾ ← 9절의 주인공 |
| **write amplification** | 쓰기 증폭 | 인덱스가 있으면 삽입마다 그것도 갱신해야 함 |
| **offset paging / keyset paging** | — | 7절. keyset은 **seek method** 라고도 부름 |

---

### ⁽¹⁾ B-tree — 왜 순서가 중요한가

정렬된 것에서 무언가를 찾는 건 빠릅니다. 문제는 **무엇을 기준으로 정렬됐느냐**입니다.

`(a, b)` 인덱스는 **먼저 `a` 로 정렬하고, `a` 가 같은 것끼리 `b` 로** 정렬합니다. 그래서:

- `where a = ?` → **좋습니다.** 한 구간으로 내려갑니다
- `where a = ? order by b` → **가장 좋습니다.** 내려간 구간이 이미 `b` 순입니다
- `where b = ?` → **나쁩니다.** `b` 는 전체에 흩어져 있습니다

**같은 두 컬럼이라도 순서가 다르면 다른 인덱스입니다.**

### ⁽²⁾ `EXPLAIN` — 추측을 끝내는 도구

```sql
explain (analyze, buffers)
select ... ;
```

**계획만 보려면 `EXPLAIN`, 실제로 돌려보고 실측까지 보려면 `EXPLAIN ANALYZE`.** 3장 7.1의 *"블로그가 아니라 로그"* 와 같은 자리입니다 — **인덱스에 대해서는 이게 로그입니다.**

### ⁽³⁾ 선택도·통계·쏠림 — 셋이 한 덩어리입니다

플래너는 *"이 조건이 몇 행이나 남길까"* 를 **추정**하고, 그 추정으로 계획을 고릅니다. 추정의 근거가 **통계**이고, 통계는 `ANALYZE` 가 수집합니다.

**그리고 여기가 이 장에서 제일 미묘한 부분입니다.** 추정이 틀렸다고 항상 손해가 나는 게 아닙니다. **손해가 나려면 추정이 계획의 경계를 넘어야** 합니다.

모든 값이 비슷한 수의 행을 갖는 **균등한** 데이터에서는, 추정이 5배 틀려도 경계 근처에 가지 않습니다. **쏠림이 있어야 추정이 하중을 받습니다.** 9절이 그것을 재고, 그 사실이 이 저장소의 실험 하나를 통째로 무효화했습니다.

## 3. 다섯 인덱스를 나란히

`attempt` 300만 행. 3회 중앙값, 밀리초, 웜.

| 인덱스 | 얕은 페이지 | **깊은 페이지** (offset 2000) | keyset | 크기 | 첫 스캔 노드 |
|---|---:|---:|---:|---:|---|
| **없음** | **36.6** | 37.1 | 41.7 | — | Parallel Seq Scan |
| **`(learner_id, attempted_at)`** | **0.056** | **0.326** | **0.052** | 90 MB | Index Scan |
| `(attempted_at, learner_id)` | **0.197** | **37.3** | 0.285 | 90 MB | Index Scan / **깊이에서 Seq** |
| `(learner_id, attempted_at)` + `INCLUDE` | 0.056 | 0.256 | 0.065 | **168 MB** | Index Only Scan |
| `(correct)` | 38.5 | 36.7 | 40.9 | 20 MB | Parallel Seq Scan |

**36.6 ms → 0.056 ms. 약 650배.**

그런데 이 표에서 배울 것은 650배가 아닙니다. **세 번째 줄입니다.**

## 4. 컬럼 순서가 발견입니다 — **틀린 인덱스도 쓰입니다**

`(attempted_at, learner_id)` 는 **같은 두 컬럼이고, 같은 90 MB이고, 실제로 사용됩니다.**

```
인덱스 없음                       36.6 ms
(attempted_at, learner_id)         0.197 ms      ← 186배 빨라짐. Index Scan.
```

**어떤 리뷰든 통과합니다.** *"인덱스 걸었고, `EXPLAIN` 봤고, Index Scan 나오네, 통과"* — 실제로 그렇게 됩니다.

### 깊이에서 무너집니다

```
(attempted_at, learner_id),  OFFSET 2000   →   Parallel Seq Scan,  37.3 ms
```

**인덱스가 있는데 쓰지 않기로 결정됩니다.** 그리고 그 결정은 **옳습니다** — 그 지점부터는 테이블을 통째로 읽는 게 실제로 더 쌉니다.

### 왜 그런가

1.1의 전화번호부입니다. 선행 컬럼이 `attempted_at` 이면 **시간 순으로 전역 정렬**되고, 한 학습자의 행은 그 안에 **흩어져** 있습니다. 그래서 한 학습자로 좁히려면 **걸어야** 하고, 어느 깊이부터는 플래너가 포기합니다.

`(learner_id, attempted_at)` 은 한 학습자의 행을 **연속으로, 이미 시간 순으로** 놓습니다. 내려가서 스무 행 뒤로 걷는 것으로 끝납니다.

> **옳은 인덱스와 그럴듯한 인덱스의 차이는,
> 테스트가 페이지를 넘기기 전까지 보이지 않습니다.**

**인덱스가 쓰이는지 확인하는 테스트는 쉽고, 그 테스트는 이 결함을 못 잡습니다.**

## 5. 한 번도 선택되지 않은 인덱스

`(correct)` — 300만 행짜리 불리언 컬럼입니다. **서로 다른 값이 둘뿐입니다.**

**열두 번의 실행에서 PostgreSQL이 한 번도 고르지 않았습니다.**

당연합니다. `correct = true` 로 좁혀도 **절반이 남습니다.** 절반을 인덱스로 찾아 힙을 왔다 갔다 하느니 테이블을 순서대로 읽는 게 쌉니다.

**그런데 값은 치릅니다.**

```
20 MB    저장 공간
+        append-only 테이블에 들어오는 모든 삽입마다 쓰기 증폭
=        돌려주는 것 없음
```

이걸 굳이 잰 이유가 있습니다.

> **이것은 누군가 쿼리에서 `WHERE correct = true` 를 보고
> *"인덱스된 컬럼이 빠르지"* 라고 추론할 때 정확히 추가되는 인덱스입니다.**

**카디널리티가 낮은 컬럼의 인덱스는 대개 비용만 있는 인덱스입니다.**

## 6. 커버링 인덱스를 안 실은 이유

`INCLUDE (...)` 를 붙이면 **Index Only Scan** 이 나옵니다 — 힙을 아예 안 건드립니다. 기법이 약속한 결과가 그대로 나왔습니다.

| | `(learner_id, attempted_at)` | `+ INCLUDE` |
|---|---:|---:|
| 얕은 | 0.056 ms | 0.056 ms |
| 깊은 | 0.326 ms | 0.256 ms |
| keyset | 0.052 ms | **0.065 ms** |
| 크기 | **90 MB** | **168 MB** |

**저장 공간 87% 더 쓰고, 차이는 측정 잡음의 가장자리이고, 넷 중 하나에서는 오히려 느립니다.**

**안 실었습니다.** 다만 이 결정에 조건을 달아뒀습니다.

> 이 숫자들은 전부 **커넥션 하나**로 잰 것입니다. 2장에서 봤듯 혼자면 140 ms 인 문장이
> 8.5개 동시에 돌면 555 ms 가 됩니다. **힙 접근을 피하는 이득은 캐시가 경합할 때 커집니다.**
> 이 결정이 **동시성에 가장 노출된 결정**이고, 그 조건에서는 **미측정**입니다.

## 7. `OFFSET` 대 keyset — **여기서는 표준 조언이 값을 못 합니다**

*"깊은 페이징에는 `OFFSET` 대신 keyset을 써라"* 는 널리 옳은 조언입니다. **얼마나 옳은지는 접근 패턴이 정합니다.**

### 이 도메인이 실제로 하는 것 — 한 학습자로 한정, 약 3,000행

| | 중앙값 |
|---|---:|
| `OFFSET 0` | 0.054 ms |
| `OFFSET 1000` | 0.158 ms |
| `OFFSET 2000` | 0.240 ms |
| `OFFSET 2900` | 0.473 ms |
| **keyset, 같은 페이지** | **0.057 ms** |

**8.3배입니다. 그리고 지는 쪽이 0.5 ms 를 씁니다.**

### 이 도메인이 하지 않는 것 — 테이블 전체를 페이징

| | 중앙값 |
|---|---:|
| `OFFSET 0` | 0.054 ms |
| `OFFSET 100,000` | 30.5 ms |
| `OFFSET 1,000,000` | 228.7 ms |
| `OFFSET 2,500,000` | **701.2 ms** |
| **keyset, 같은 페이지** | **0.239 ms** |

**2,930배이고, 깊이에 비례해 계속 자랍니다.** `OFFSET` 이 행을 걸어서 세기 때문입니다.

### 그래서 keyset을 채택하지 **않았습니다**

**두 표는 같은 메커니즘입니다.** 다른 것은 접근 패턴뿐입니다.

> **두 번째 표만 중요하고, 그것도 패턴이 무제한일 때만 중요합니다.**
> 이 도메인은 한 학습자의 3,000행 안에서만 페이징하므로, keyset은 **API를 바꿔서 0.4 ms 를
> 버는 일**이 됩니다.

**널리 옳은 조언이 여기서 값을 못 하는 이유는 조언이 틀려서가 아니라, 그 조언이 옳아지는 조건이 여기 없기 때문입니다.** 그리고 **관리자 화면이나 내보내기 경로가 학습자를 가로질러 페이징하기 시작하면 이 결정은 틀린 결정이 됩니다.**

## 8. 낡은 통계가 재현되지 않았습니다 — **두 번**

T4에는 가닥이 다섯이었고 넷은 재현됐습니다. 다섯째 — **대량 적재 뒤의 낡은 플래너 통계** — 는 **두 번 시도해서 두 번 다 안 나왔습니다.**

| | 플래너 추정 | 계획 | 중앙값 |
|---|---|---|---:|
| `ANALYZE` 전 | rows=15000 | Index Scan | 0.101 ms |
| `ANALYZE` 후 | rows=2994 (실제 3000) | Index Scan | 0.128 ms |

**계획이 바뀌지 않았습니다.**

### 첫 번째 이유 — `CREATE INDEX` 가 통계를 고칩니다

통계를 *"한 번도 분석 안 함"* 상태로 되돌리고 인덱스를 만들었더니, **`ANALYZE` 를 돌리기 전에 이미 `reltuples = 3000000` 이 들어가 있었습니다.**

`CREATE INDEX` 는 어차피 테이블을 전부 읽습니다. **읽는 김에 행 수와 페이지 수를 갱신합니다.**

> **대량 적재 후 인덱스를 만들면 통계가 부분적으로 복구됩니다.**
> 리포트가 *"어디서도 읽은 적 없다"* 고 적었고, 저도 못 봤습니다.

**그리고 이건 재현 실패의 절반만 설명합니다.** 나머지 절반이 다음 두 절입니다.

## 9. 데이터가 가리고 있었습니다

리포트가 §8에 의심을 하나 적어뒀습니다.

> *"이 데이터셋에는 **skew가 없다.** 모든 학습자가 정확히 3,000개씩, 균등하게 갖는다.
> … **내가 만든 생성기가 T4의 한 갈래를 통째로 가리고 있을 수 있다.**"*

**사흘 뒤에 확인했고, 맞았습니다.** 학습자 하나에게 테이블의 **30%** 를 주고 같은 실험을 반복했습니다.

| | 계획 | 추정 | 실제 | 비 | 시간 |
|---|---|---:|---:|---:|---:|
| 균등, 통계 삭제 | Bitmap Heap Scan | 5,000 | 1,000 | 5배 과대 | 1.7 ms |
| 균등, `ANALYZE` 후 | Bitmap Heap Scan | 995 | 1,000 | 1.0배 | 1.1 ms |
| **쏠림, 통계 삭제** | **Bitmap Heap Scan** | **5,000** | **300,000** | **60배 과소** | **46.2 ms** |
| **쏠림, `ANALYZE` 후** | **Parallel Seq Scan** | 125,375 | 100,000 | 1.25배 | **29.2 ms** |

**쏠림이 있으면 계획이 바뀝니다.** 그게 T4의 다섯째 가닥이고, **재현됐습니다.**

### 왜 균등하면 안 무는가

플래너는 *"이 조건이 몇 행을 남길까"* 를 추정하고 그 추정으로 계획을 고릅니다.

**균등한 컬럼에서는 모든 값이 같은 수의 행을 갖습니다.** 그래서 추정이 5배 틀려도, **틀린 방향이 어떤 결정 경계에도 닿지 않습니다.** `learner_id = 1` 과 `learner_id = 743` 이 같은 비용의 같은 쿼리이고, 낡은 추정은 옳은 추정을 그냥 배수로 늘린 것입니다.

**쏠림이 추정에 하중을 겁니다.** 한 값이 30%를 갖고 나머지가 0.07%씩 가지면, **같은 기본 추정이 거의 모든 학습자에게 맞고 한 명에게 파국적으로 틀립니다.** 그리고 플래너는 분포를 모르면 **지금 보고 있는 게 어느 쪽인지 알 방법이 없습니다.**

> **균등한 데이터셋은 플래너를 옳게 만드는 것이 아니라,
> 플래너의 옳음을 무관하게 만듭니다.**

### 곁가지 하나 — 병렬 계획의 행 수는 워커당입니다

마지막 줄의 `actual 100,000` 은 **총합이 아니라 워커 하나당**입니다. 병렬 계획 노드는 루프당 수치를 보고합니다 — 워커 셋 × 100,000 이 같은 300,000 입니다.

**추정치도 워커당이라 1.25배 비교는 같은 단위끼리의 비교입니다.** 이 문단 없이 `100,000` 을 `300,000` 옆에 적으면 모순처럼 읽힙니다.

## 10. 질문의 모양 — **이 장의 진짜 주제**

8절에는 이유가 **하나 더** 있고, 이게 이 장에서 가장 오래 쓸 교훈입니다.

그 실험이 쓴 쿼리는 이것이었습니다.

```sql
select ... from attempt where learner_id = ?
 order by attempted_at desc limit 20
```

**이 쿼리는 선택도가 무엇이든 인덱스로 처리됩니다.** 스무 행만 필요하고 인덱스가 이미 그 순서로 정렬돼 있으니까요.

> **그러니 추정이 아무리 틀려도 그 계획을 바꿀 수 없었습니다.**
> **질문이, 답을 담을 수 없는 모양으로 던져졌습니다.**

재현하려면 **집계 쿼리**로 물어야 했습니다 — 행을 많이 만져야 계획 선택이 하중을 받으니까요.

### 그런데 여기에 대가가 있습니다

리포트가 그 대가를 스스로 적었습니다.

> **효과를 보여줄 수 있는 쿼리를 고르는 것 자체가, 애플리케이션이 실제로 하는 일에서
> 한 걸음 멀어지는 것이다.**
>
> **그리고 배포되는 것은 위의 쿼리입니다.**

이게 실험 설계의 정직한 딜레마입니다.

| | |
|---|---|
| 배포되는 쿼리로 재면 | **효과가 안 나온다** — 그 모양이 효과를 담지 못한다 |
| 효과가 나오는 쿼리로 재면 | **애플리케이션이 안 하는 일을 잰 것이다** |

**둘 다 참이고, 어느 쪽도 답이 아닙니다.** 할 수 있는 것은 **어느 쪽으로 갔는지 적어두는 것**뿐입니다.

### 앞 장들과 나란히 놓으면

| | 재현이 안 될 때, 무엇을 의심하나 |
|---|---|
| **3장 5.3** | **장치**가 고장났나 — 검출될 것을 심어본다 |
| **3장 5.5 · 이 장 9절** | **데이터**가 가리고 있나 — 분포를 본다 |
| **이 장 10절** | **질문**이 답을 담을 수 있는 모양인가 |

> **셋 다 "결함이 없다"와 겉보기가 똑같습니다.**
> 그리고 셋 다, **의심하지 않으면 그냥 통과합니다.**

## 11. 게이트가 약하고, **약한 것이 요점입니다**

인덱스 집합을 **정확한 목록**으로 단언하는 게이트가 있습니다. 삭제도 실패하고, **리포트가 정당화하지 않은 추가**도 실패합니다.

**그런데 이 게이트는 보기보다 약하고, 리포트가 그걸 스스로 적었습니다.**

> **인덱스가 *존재한다* 를 단언하지, *쓰인다* 를 단언하지 않습니다.**
> 그리고 4절은 **존재하고 쓰이는데도 틀린 인덱스**에 대한 절 전체입니다.

즉 **미래의 마이그레이션이 컬럼 순서를 뒤집어도 이 게이트는 통과시킵니다.** 깊은 페이지에서 0.326 ms 가 37.3 ms 가 되는 그 변경을요(리포트는 얕은 페이지 기준으로 그 회귀를 660배로 적습니다).

`EXPLAIN` 출력을 단언하는 게이트가 더 강할 것이고, **아직 아무것도 그렇게 하지 않습니다. 미측정.**

> **리포트가 자기 게이트를 "이 리포트가 쓰지 않은 가장 값진 테스트"라고 부릅니다.**
> 게이트를 갖는 것과 **그 게이트가 무엇을 못 잡는지 아는 것**은 다른 일이고,
> 후자를 적어두지 않으면 게이트는 **안심의 근거**가 됩니다.

## 부록 — 어디까지가 관측이고 어디부터가 설명인가

### ① 관측된 것

| | 출처 |
|---|---|
| 다섯 인덱스 매트릭스, 36.6 ms → 0.056 ms | `R3` §3.1, red `cceec6a` / green `V2__attempt_learner_time_index.sql` |
| `(attempted_at, learner_id)` 가 얕은 곳에서 쓰이고 깊이에서 무너짐 | `R3` §3.2 |
| `(correct)` 가 열두 번의 실행에서 한 번도 선택되지 않음 | `R3` §3.3 |
| `INCLUDE` 가 87% 크고 차이는 잡음 수준 | `R3` §3.4 |
| `CREATE INDEX` 가 `reltuples` 를 복구함 | `R3` §3.5 |
| offset/keyset 두 표 | `R3` §3.6 |
| 쏠림에서 계획이 뒤집힘, 60배 과소추정 | `R13` §3 |

환경: PostgreSQL 16.14, `attempt` 300만 행, 3회 중앙값, **전부 커넥션 하나로.**

### ② 설명이고 관측이 아닌 것

- **1.1의 전화번호부.** B-tree 의 정렬 성질을 설명하는 비유이고, 측정이 아닙니다.
- **5절의 *"누군가 `WHERE correct = true` 를 보고 인덱스를 건다"*.** 그럴듯한 시나리오이고 이 저장소에서 실제로 일어난 일은 아닙니다. **일부러 재본 것**입니다.

### ③ 남는 위험 — 리포트가 스스로 적은 것

- **아무것도 계획을 단언하지 않습니다**(11절). 컬럼 순서를 뒤집는 마이그레이션이 게이트를 통과합니다. **이 리포트가 쓰지 않은 가장 값진 테스트입니다.**
- **모든 숫자가 커넥션 하나입니다.** 동시성 아래에서 순위가 움직일 수 있고, **커버링 인덱스의 기각이 가장 많이 노출된 결정**입니다.
- **`INCLUDE` 결정이 0.07 ms 차이 위에 서 있습니다.** 실행 간 산포 안이고, 세 번으로는 못 가릅니다. *"측정 가능한 차이 없음"* 으로 보고했지 *"더 빠름"* 으로 보고하지 않았지만, **표본을 늘리면 부호가 바뀔 수 있습니다.**
- **인덱스 크기를 갱신이 없는 테이블에서 쟀습니다.** `attempt` 는 append-only 이고 대량 적재됐습니다. **블로트, `REINDEX` 비용, `(correct)` 인덱스가 유발할 쓰기 증폭은 전부 미측정입니다.**
- **keyset 기각은 현재 엔드포인트에 대한 것입니다.** 관리자나 내보내기 경로가 학습자를 가로질러 페이징하면 7절 두 번째 표가 적용되고 **결정이 뒤집힙니다.**
- **결론을 깨뜨리는 것**: `attempt` 를 읽는 방식의 변경. 여기 모든 숫자가 *"읽기는 한 학습자로 한정되고 시간 순으로 정렬된다"* 를 가정합니다. **다르게 읽는 리포트는 처음부터 다시 시작합니다.**

### ④ 이 장이 스스로 만든 위험

9절의 실험은 **일부러 쏠리게 만든 데이터**에서 돌았습니다. 그것이 **배포되는 데이터셋이 아닙니다.**

즉 이 장은 *"우리 데이터가 결함을 가리고 있었다"* 를 보여주려고 **또 다른 인공 데이터**를 만들었습니다. 10절의 딜레마가 여기에도 그대로 적용되고, **리포트가 그것을 §8에 적어뒀습니다.**
