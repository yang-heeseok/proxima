## 2. 측정 대상의 구조 (읽어서 확인한 것)

`RecommendationController.recommend()` 의 세 단계입니다.

```
(1) recommendations.nextItems(learnerId, limit)      @Transactional(readOnly = true)
      ├ findRecommendedItemIds(...)   네이티브 쿼리, id 목록만
      └ items.findAllById(ids)        엔티티 로드
    ← 여기서 트랜잭션이 끝난다

(2) items.associate { it.id!! to it.conceptPrimary.name }
    ← 트랜잭션 밖에서 지연 로딩. OSIV 세션 안

(3) content.renderHints(ids)          Thread.sleep(delayMillis)  기본 150ms
    ← DB 와 무관. 스레드가 파킹된다

(4) 응답 직렬화 → 요청 종료 → OSIV 세션 close
```

**확인된 사실 (코드에서 직접 읽음)**

- `Item.conceptPrimary` 는 `@ManyToOne(fetch = FetchType.LAZY, optional = false)` —
  **명시적으로 LAZY**. 즉 (2)는 확실히 쿼리를 낸다. *"이미 EAGER 로 다 읽혀서 (2)가
  아무 일도 안 한다"* 는 가능성은 배제된다.
- (1)은 **왕복이 두 번**이다. id 목록 쿼리 + `findAllById`.
- `ContentGateway` 는 `Thread.sleep` 이고 지연은 `proxima.content-gateway.delay-ms`
  프로퍼티, 기본 150ms.
- **green 경로가 이미 쓰여 있다.** `findRecommendations` 는 프로젝션(`RecommendationRow`)을
  돌려주고, 주석이 *"Nothing it returns can trigger a database round trip later, so the
  connection goes back to the pool when the transaction ends"* 라고 적고 있다.

**확인하지 않은 것**

- HikariCP 풀 크기. 기본 10으로 알려져 있으나 이 저장소에서 확인하지 않았다.
  아래 산술은 전부 **10을 가정**한다.
- `hibernate.connection.handling_mode` 의 실제 값.

## 3. 예측 ① — 핵심 질문

> **(3)의 `Thread.sleep` 동안 `hikaricp.connections.active` 는 1인가 0인가?**

### 나는 **1** 에 건다. 확신도 **70%**.

**근거.** Hibernate 의 resource-local(비 JTA) 기본 커넥션 처리 방식은
`DELAYED_ACQUISITION_AND_RELEASE_AFTER_TRANSACTION` 으로 알고 있다. 두 부분으로 읽는다.

- *DELAYED_ACQUISITION* — 세션이 열릴 때가 아니라 **첫 JDBC 작업 때** 커넥션을 얻는다.
- *RELEASE_AFTER_TRANSACTION* — **트랜잭션이 완료될 때** 반납한다.

그러면 (2)가 문제가 된다. **(2)는 트랜잭션 밖에서 실행된다.** 완료될 트랜잭션이 없으므로
반납을 촉발할 사건이 없다. 따라서 (2)에서 얻은 커넥션은 **세션이 닫힐 때까지** 붙어 있고,
OSIV 가 그 시점을 요청 끝으로 미뤄놨다.

### 반대 가설 (30%)

Hibernate 7.x 가 트랜잭션이 없을 때 문장 단위로 반납하거나, Spring Boot 가 다른
handling mode 를 설정하고 있다면 (3) 동안 `active` 는 **0** 이다. 그러면 OSIV 는 이
경로에서 아무 비용도 물리지 않는다.

## 4. 예측 ② — 곡선의 모양

숫자 하나보다 이쪽이 더 잘 틀립니다. 그래서 더 유용합니다.

**예측 A (내가 거는 쪽)**

```
active
  1 |    ┌────┐                ┌──────────────────────────┐
    |    │(1) │                │ (2)  (3) sleep  (4) 직렬화 │
  0 |────┘    └────────────────┘                          └──── 요청 종료
         ↑         ↑            ↑                          ↑
       트랜잭션   트랜잭션      첫 지연로딩                 세션 close
        시작      완료→반납      →재획득
```

**핵심은 가운데 골짜기입니다.** (1)이 끝나면 트랜잭션이 완료되므로 **한 번 반납된다.**
그리고 (2)에서 **다시 얻는다.**

> **이건 통념과 다릅니다.** "OSIV 는 요청 내내 커넥션을 쥔다"가 아니라
> **"트랜잭션 밖 지연 로딩이 커넥션을 재획득하고, 끝낼 트랜잭션이 없어서 못 놓는다"** 입니다.
> **범인은 OSIV 단독이 아니라 OSIV + 트랜잭션 밖 지연 로딩의 조합입니다.**

**예측 B (반대 가설)** — (2)의 SELECT 하나하나마다 올라갔다 내려가고, (3) 동안 0.

### 그래서 `교재 2장` §4 의 그림은 이미 틀렸을 수 있습니다

2장 §4 의 타임라인은 커넥션을 **연속으로** 쥐는 것처럼 그려져 있습니다. A가 맞더라도
**가운데 반납 구간이 빠져 있습니다.** 측정 후 고쳐야 합니다.

## 5. 예측 ③~⑤ — 부수 예측

### ③ (2)가 내는 SELECT 개수 (`limit=10`)

**1~10개. 중앙값 추정 4~8개.** 각 `Item` 이 자기 `conceptPrimary` 프록시를 갖지만, 두
아이템이 같은 개념을 가리키면 영속성 컨텍스트가 같은 프록시를 돌려주므로 쿼리가 줄어든다.
추천 규칙이 **학습자가 아직 숙련하지 못한 개념**을 겨냥하므로 개념이 몇 개로 뭉칠 것이다.

**이건 전형적인 N+1 이고, T7 이 세게 될 숫자입니다.** T1 안에 T7 의 재료가 같이 들어 있다.

### ④ k6 200 VU 의 p99

풀 10 가정. 요청당 커넥션 점유 시간 `W` 로 `λ_max = 10 / W`.

| | 커넥션 점유 `W` | `λ_max` | 200 VU 폐루프 주기 | **p99 예측** |
|---|---|---|---|---|
| **A** | (1) ~20ms + (2)~(4) ~160ms ≈ **180ms** | ~55 req/s | 200 ÷ 55 ≈ 3.6s | **3~5초** |
| **B** | (1) ~20ms + (2) ~5ms ≈ **25ms** | ~400 req/s | 200 ÷ 400 ≈ 0.5s | **0.5~0.9초** |

**A 와 B 는 p99 에서 대략 5배 차이입니다.** 이게 이 실험의 판별력입니다.

`pending` — A: 지속적으로 100 이상. B: 훨씬 낮고 요동친다.

### ⑤ 데이터베이스 CPU

**A 에서 낮게 나온다.** 이게 2장 전체의 진단 문장입니다 — *줄은 긴데 뒷단은 한가하다.*
`pending` 이 높은데 DB CPU 가 낮으면 느린 것은 DB 가 아니다.

## 6. 이 실험을 무효화할 수 있는 것 — 가장 큰 위험

> **`findRecommendedItemIds` 자체가 느리면, `W` 를 쿼리 시간이 지배해서
> OSIV 의 효과가 묻힙니다.**

근거가 있습니다. `RecommendationQueries` 주석이 **`attempt` 300만 행에
`(learner_id, attempted_at)` 인덱스가 없다**고 적고 있고, 그게 `T4` 의 주제입니다. 그
`NOT EXISTS` 가 학습자마다 스캔을 돌면 (1)이 수십~수백 ms 가 될 수 있습니다.

그러면 A 든 B 든 `W` 가 커져서 **두 가설의 차이가 5배에서 1.5배로 줄어듭니다.**

**확신도 50% 로 예측합니다: T1 의 첫 실행은 OSIV 가 아니라 쿼리 비용에 지배당한다.**
그 경우 순서를 바꿔야 합니다 — `delay-ms` 를 키워서 sleep 이 확실히 지배하게 만들거나,
아니면 T4 를 먼저 하거나. **어느 쪽이든 그건 발견이지 실패가 아닙니다.**

부차적 위험 둘:
- `Thread.sleep` 중에는 스레드가 파킹되므로, **가상 스레드가 켜져 있으면** 스레드 병목이
  사라져 커넥션 병목이 더 선명해진다. 설정을 확인하지 않았다.
- 200 VU 폐루프에서 워밍업 30초가 풀을 이미 포화시킨 상태로 측정 구간에 들어갈 수 있다.
  그건 의도된 설계다(`load/README.md`).

## 8. 내가 못 보고 있을 축

0장 §0.5(3)이 기록하라고 한 칸입니다. **채움 2026-08-12.**

### 1. 상태를 확인하지 않고 "봉인"을 선언한 것

가장 먼저 적어야 할 것이고, 예측 내용과는 무관합니다. **문서의 값어치를 통째로 정하는
전제를 검증 없이 썼습니다.** 확인 비용은 명령어 하나였습니다.

### 2. `W` 를 "내가 통제하는 항"으로만 봤다

예측 ①~⑤가 전부 *"OSIV 가 `W` 를 늘리는가"* 를 물었습니다. **`W` 의 가장 큰 항이 쿼리
그 자체일 수 있다는 것은 ⑥에 단서로만 달았지 예측의 중심에 두지 않았습니다.**

실측: 커넥션 점유 385 ms 중 **DB 시간이 235 ms.** 다수가 쿼리였습니다.

### 3. 병목이 하류에 있을 가능성을 세지 않았다 — **이게 제일 큽니다**

예측 A 와 B 는 **둘 다 "풀이 병목"을 전제했습니다.** 실측에서 병목은 데이터베이스였고,
그래서 **처방의 순위가 뒤집혔습니다** — 교과서적 수정(arm B, 트랜잭션 안에서 다 가져오기)이
유휴 점유를 40%→15% 로 줄이고도 **처리량을 26 → 18 req/s 로 떨어뜨렸습니다.**

**내 예측표에는 "처방이 역효과일 수 있다"는 칸이 아예 없었습니다.**

> 예측 ①~⑤는 전부 *"커넥션이 얼마나 오래 붙잡혀 있나"* 를 물었습니다.
> 정작 답을 정한 것은 *"그 커넥션이 붙잡혀서 무엇을 하고 있었나"* 였습니다.

### 4. 답이 나온 뒤에도 엉뚱한 측정을 기다렸다

②를 **하루 동안 "미해결"로 분류하고 있었습니다.** 더 촘촘한 시계열(0.5초보다 짧은 샘플링)을
기다렸기 때문입니다. 답을 준 것은 **해상도가 아니라 다른 arm** 이었습니다 — 지연 로딩이
일어나지 않는 구성에서도 커넥션이 계속 붙잡혀 있었고, 그것으로 가설이 죽습니다.

> **정밀도를 올려서 답할 문제와 대조군을 바꿔서 답할 문제를 구분하지 못했습니다.**
> 그리고 후자가 대개 더 싸고 더 결정적입니다.

### 5. 커넥션 하나를 프로세스 하나로 셌다

`Workers Planned: 2`, 병렬 워커 4~7개 상시. **풀 크기와 `max_connections` 는 세는 단위가
다릅니다.** 이 축은 내 예측에 존재하지도 않았습니다.
