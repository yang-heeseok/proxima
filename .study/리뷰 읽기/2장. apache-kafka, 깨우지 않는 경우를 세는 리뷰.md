## 2.4 그런데 제목이 답을 흘렸다 — §0.5(3) 의 첫 번째 균열

§0.5(3) 은 *"디프만 보고 지적할 점 3개를 적는다"* 로 시작한다. 그 전제는 **디프가 유일한
입력**이라는 것이다. 1장의 openjdk #26461 은 제목이 *"Add no-argument `codePointCount`
method to String"* 이었다 — **기능 추가이고, 결함을 말하지 않는다.**

Kafka 는 JIRA 로 굴러간다. 제목이 `KAFKA-20854 A more obvious busy loop due to KIP-909` 이고,
본문은 **결함의 완전한 서술**이다.

> `FetchRequestManager` currently wakes up the `FetchBuffer` unconditionally whenever
> `prepareFetchRequests()` returns no requests to send. […] the application thread and the
> background `ConsumerNetworkThread` can enter a tight loop […]
>
> This is a pre-existing issue introduced with the non-blocking `AsyncPollEvent` redesign in
> KAFKA-18376. However, **KIP-909's async bootstrap DNS resolution extends the "no node
> available" window from effectively instantaneous to up to `bootstrapResolveTimeoutMs`,
> making the busy loop much more visible.**

**결함이 무엇인지를 맞히는 게임은 여기서 성립하지 않는다.** 그래서 예측 대상을 옮겼다 —
*"무엇이 터질까"* 가 아니라 **"이 고침의 무엇이 리뷰에서 걸릴까"** 로.

> **이건 후퇴가 아니라 다른 훈련이다.** 현업에서 받는 PR 의 대부분은 티켓이 붙어 있고
> 문제가 이미 적혀 있다. **"문제는 안다. 이 해결이 옳은가"** 가 실제로 더 흔한 리뷰다.
> 다만 **0장이 그 두 모드를 구분하지 않고 있었고**, 구분하지 않으면 채점이 무의미해진다.

## 2.6 채점 — 그리고 **병합된 PR 의 디프는 리뷰의 산출물이다**

리뷰어 코멘트는 20개다(29 − 작성자 9).

| | 판정 | 실제 |

| **P2** | **적중** | Andrew: *"the naming here is a bit strange… Could it be `canWakeBufferIfNoFetchRequestsToSend` or similar? Maybe the `fetchRequestPreparer` should be able to return this information in some way directly."* |
| **P3** | **위치 적중 · 부호 반대** | 지적이 아니라 **칭찬**이었다. lianetm: *"nice, this was a big gap I just realized (yesterday) that we had (not waking up on all responses)"* |
| **P5** | **적중(절반 베팅)** | lianetm 이 group 없는 컨슈머를 물었고, 셋이 합의해 그 게이트를 **삭제**했다 |

| P4 | 빗나감 | 계층 질문은 나왔으나 **"어느 스레드가 결정을 소유하는가"** 로 나왔다 |
| P6 | 빗나감 | 리뷰가 아니라 **CI 가** 잡았다(§2.8 축 ③) |

### P2·P5 는 적중이 아니라 **답안지를 읽은 것**이었다

**내가 읽은 디프에 이미 `canWakeBufferIfNoFetchRequestsToSend` 라는 이름이 들어 있었다.**
그 이름은 Andrew 가 제안한 이름이다. 즉 나는 **리뷰가 고친 뒤의 코드**를 보고
*"리뷰어가 이 이름을 문제 삼을 것"* 이라고 예측했다.

같은 일이 P5 에서도 일어났다. 디프에 `isCommittedOffsetsManagementEnabled()` **삭제**가
보였고, 나는 *"리뷰어가 이 변경을 물을 것"* 이라고 적었다. 실제 인과는 정반대다 —
**리뷰어의 질문이 그 삭제를 만들었다.** 같은 줄, 화살표 반대.

세어 보면 이렇다. **리뷰어 코멘트 20개 중 최소 6개는 그 결과가 내가 읽은 디프에
이미 반영돼 있었다.**

| 코멘트 | 요구 | 내가 읽은 디프의 상태 |
| --- | --- | --- |
| Andrew | 이름을 `canWakeBufferIfNoFetchRequestsToSend` 로 | **그 이름으로 들어 있음** |
| Andrew | `RequestManagers` 의 두 지역변수를 `final` 로 | **`final` 붙어 있음** |
| chia7712 | `Collections.emptyMap()` → `Map.of` | **`Map.of()` 로 들어 있음** |
| chia7712 | 빈 파티션 사유에 DNS 해석도 적어라 | **주석에 "bootstrap DNS resolution" 들어 있음** |
| lianetm | 주석이 이상하게 읽힌다, 재배열해라 | **재배열돼 있음** |
| lianetm | group 없는 컨슈머는? | **게이트가 삭제돼 있음** |

**30%다.** 그리고 이건 이 PR 의 특성이 아니라 **병합된 PR 의 정의**다.
GitHub 의 `Files changed` 는 언제나 **최종 상태**를 보여준다. 병합된 PR 에서 §0.5(3) 을
하면, 예측의 재료가 이미 **리뷰의 결과물**이다.

> **병합된 PR 에서 디프를 보고 예측하는 것은, 답을 보고 문제를 맞히는 것이다.**

그리고 이 오염은 **한 방향으로만 작동해서 더 위험하다.** 리뷰가 고친 자리에는 흉터가
남아 있다 — 이상하게 긴 이름, 유난히 구체적인 주석, 방금 삭제된 헬퍼. 그 흉터가
**예측을 그리로 끌어당긴다.** 적중률이 올라가고, 올라간 만큼 배운 것은 없다.

### 그리고 "열린 PR 이면 괜찮다"고 쓰려다 반증을 만났다

이 절의 대책 1번을 처음에 *"열려 있는 PR 을 읽는다 — 결론이 없으므로 오염이 없다"* 로 썼다.
1장이 정독한 openjdk **#26461 이 열려 있었으니 1장은 깨끗하다**는 주장을 붙이려고
상태를 조회했다. **응답이 그 주장을 그 자리에서 깼다.**

```
state open | merged None | created 2025-07-24 | commits 42
```

**13개월 동안 열려 있으면서 커밋 42개.** 40번 넘게 고쳐졌다는 뜻이고, 그 수정의 대부분은
리뷰에 대한 응답이다. **오염의 원인은 병합이 아니라 수정이다.** `Files changed` 는 언제나
현재 head 를 보여주므로, **리뷰를 받고 고쳐진 PR 은 열려 있어도 리뷰의 산출물이다.**

> **열림/닫힘은 오염과 무관하다.** 그리고 이 오답은 **무죄를 증명하려고 부른 조회가
> 같은 응답에 반증을 담아 온** 경우다 — 교재 9장이 세는 부류이고, 여기서 잡은 것은
> 어떤 검사도 아니라 **주장을 뒷받침할 숫자를 실제로 찾아본 것**뿐이다.

**대책 셋. 신뢰도 순으로.**

| | 대책 | 신뢰도 |
| --- | --- | --- |
| **①** | **첫 커밋의 디프를 본다** — `/pull/{n}/commits` 의 첫 SHA. 이 PR 은 커밋 17개이므로 리뷰 전후가 뚜렷하다 | **유일하게 확실하다** |
| ② | **리뷰 전 PR 을 읽는다** — 커밋 1~2개에 인라인 0개면 아직 아무도 안 고쳤다. **열림이 아니라 커밋 수로 판별한다** | 대체로 |
| ③ | **못 하면 세어서 적는다.** 이 장이 그렇게 했다 — 봉인 파일이 남았고 위 표로 셀 수 있다. **적중 3개 중 2개는 무효다** | 없애지 못하고 드러내기만 한다 |

### P1 은 빗나갔고, 지적했으면 **내가 틀렸을 것이다**

아무도 `SubscriptionState` 에 코멘트를 달지 않았다. 왜 안 달았는지가 이 장의
두 번째 수확이다. 파일을 열어 보면 새 메서드 열 줄 위에 이게 있다.

```java
public synchronized List<TopicPartition> fetchablePartitions(Predicate<TopicPartition> isAvailable) {
    // Since this is in the hot-path for fetching, we do this instead of using java.util.stream API
    List<TopicPartition> result = new ArrayList<>();
    ...
```

**중복은 실재한다. 그런데 그 중복이 곧 최적화다.** `hasFetchablePartitions` 는
`ArrayList` 를 할당하지 않으려고 존재하고, `forEach` 대신 명시적 for 루프를 쓰는 이유는
람다에서 조기 반환(early return)을 할 수 없어서다. **하나를 다른 하나로 구현하면
존재 이유가 사라진다.** 이 파일은 이미 스트림 API 를 버리면서까지 그걸 지키고 있었다.

`subscriptionType.equals(ENUM)` 도 마찬가지다. 이 파일은 `.equals()` 3회 · `==` 8회로
**혼재**돼 있고, 새 메서드는 **복사해 온 형제 메서드의 표기를 그대로 따랐다.**
불일치를 지적하려면 새 줄이 아니라 **파일 전체**를 걸어야 한다.

> **디프는 추가된 줄을 보여주지, 그 줄이 복사해 온 줄을 보여주지 않는다.**

내가 P1 을 쓴 이유는 단 하나 — **형제 메서드와 그 위의 주석을 읽지 않았기 때문**이고,
읽지 않은 이유는 **디프에 없었기 때문**이다. §0.5(3) 에 한 단계가 더 필요하다:
**디프에서 새 메서드를 보면, 그 파일을 열어 이웃을 읽는다.**

리뷰어 코멘트의 대부분이 같은 문장 형태를 갖는다: **"그럼 X 상태일 때는?"**

| 물은 사람 | 상태 | 결론 |

그리고 작성자의 답변이 전부 **"이 대기는 누가 끝내주는가"** 로 되어 있다.

> **paused** — 일시정지된 파티션을 다시 페치 가능하게 만드는 것은 **애플리케이션 스레드
> 자신의 `resume()` 호출뿐**이다. 깨워 줄 백그라운드 활동이 없다. 여기에 경계를 두면
> *"아무것도 안 변한 것을 반복 확인하는 주기적 기상"* 만 생긴다.
>
> **pending revocation** — `collectFetch()` 의 `inflightPoll.reconciliationCheckFuture()` 대기와
> **하트비트 매니저의 `maximumTimeToWait()`** 이 이미 촘촘하게 경계 짓는다.
> `FetchRequestManager` 가 둘 중 어느 것도 복제할 필요가 없다.

**이것이 이 장의 정식 어휘다.** 대기를 넣을 때 채워야 하는 칸은 둘이다.

| | |
| --- | --- |
| **깨움의 출처** | 누가 이 스레드를 깨우는가 |
| **경계의 출처** | 아무도 안 깨우면 **무엇이** 이 대기를 끝내는가 |

두 칸이 다 비면 무한 대기다. 첫 칸이 **너무 자주** 채워지면 busy loop 다.
**이 PR 은 후자를 고치면서 전자가 비지 않도록 지키는 작업이고, 리뷰 29개 전부가 그 검사다.**

## 2.8 내가 보지 않은 축 — 이 칸이 이 노트의 전부다 (§0.5(3)-4)

### 축 ① 깨우기 의무는 **상태가 변하는 지점**에 붙는다

P3 에서 내가 "위험"으로 읽은 줄이 리뷰어에게는 **닫힌 구멍**이었다.

```java
private void removePendingFetchRequest(Node fetchTarget, int sessionId) {
    nodesWithPendingFetchRequests.remove(fetchTarget.id());
    // Wake the buffer whenever a node stops having a request in flight, whatever the outcome
    // was: data, an empty response, a fetch session error, or a failure.
    fetchBuffer.wakeup();
}
```

이전 코드는 **성공 응답 처리 경로 안에서** `needsWakeup` 이라는 지역 변수로 판단했다.
그래서 **실패·세션 오류 경로에서는 깨우지 않았다.**

내 판단은 *"remove 라는 이름의 메서드에 부수효과"* 라는 **이름 기준**이었다.
리뷰어의 판단은 **불변식 기준**이다 — 앱 스레드의 대기는 `nodesWithPendingFetchRequests`
가 비는 것에 걸려 있으므로, **그 집합이 줄어드는 모든 지점이 깨워야 한다.**
집합을 건드리는 자리가 그 자리 하나이므로, **깨우기는 거기 있어야 한다.**

> **깨우기를 해피 패스에 두면 결과별로 빠뜨린다. 상태 변경 지점에 두면 결과와 무관해진다.**

### 축 ② 캐시된 결정과, 그 결정을 쓰는 시점 사이의 스레드 경계

**리뷰 이틀째에 lianetm 이 디프만 보고 이렇게 적었다.**

> *"also thinking races now, the 'prepare requests' that computes this […] is triggered from
> the network thread **before** polling, but then this `maximumTimeToWait` is used **after**
> the poll (so things could change in-between). […] Could that be an issue? Would it be safer
> to just determine the max wait **'live'** here?"*

작성자는 "addressed" 하고 넘어갔다. **일주일 뒤, Andrew 의 최적화 제안을 반영하려고 그
검사를 다시 네트워크 스레드로 옮겼고 — CI 가 타임아웃으로 죽었다.**

> *"that introduced a stale-cache issue and **caused a CI timeout**. […] `maximumTimeToWait()`
> runs on the network thread, and its result is **cached**. If the network thread observes that
> all fetchable partitions are buffered and returns `Long.MAX_VALUE`, but the application
> thread then **consumes that data**, the cached value becomes stale. […] The application-thread
> check acts as a **freshness guard**: it re-evaluates the buffer state right before blocking."*

**리뷰어가 디프만 보고 예측한 경쟁 상태가, 2주 뒤 CI 로 재현됐다.** 그리고 최종 설계는
둘 중 하나를 고르지 않았다 — **양쪽 다 둔다.** 네트워크 스레드가 계산한 상한과,
**블록 직전에 앱 스레드가 다시 확인하는 신선도 가드.** 대가는 보수적인 여분의 기상 한 번.

교재 4장의 잃어버린 갱신과 **같은 형태**다. 읽어 둔 값으로 판단하고 나중에 행동하면,
행동하는 시점에 그 값은 이미 참이 아닐 수 있다. **거기서는 `WHERE` 절이 신선도 가드였고,
여기서는 블록 직전의 재확인이다.**

### 축 ③ 성능 제안이 정확성을 깼고, **그 제안은 리뷰어의 것이었다**

> Andrew: *"If there are in-flight requests for all assigned partitions, I don't think we need
> to poll at `retryBackoffMs`, especially now `removePendingFetchRequest` has been improved."*

타당한 최적화다. 반영했더니 축 ②의 stale cache 가 터졌다. **작성자가 재보고,
왜 안 되는지를 써서 되돌렸다.**

**세 저장소에서 세 번 같은 모양이다.**

| 장 | 저장소 | 리뷰어의 제안 | 되돌린 근거 |
| --- | --- | --- | --- |
| 1장 | `openjdk/jdk` #26461 | 가독성 개선 루프 | 인덱스 0의 서로게이트 쌍을 건너뜀 — **jshell 로 재현** |
| **2장** | **`apache/kafka` #23014** | **불필요한 기상 제거** | **stale cache — CI 타임아웃** |
| 4장 | `hibernate/hibernate-orm` #6038 | 프로젝트 리드의 성능 제안 | 가변 객체 위의 캐시 무효화 |

> **리뷰어의 제안은 코드가 아니라 가설이다. 그것을 검증할 사람은 언제나 기여자다.**
> 그리고 셋 다 **기여자가 이겼다.** 근거가 실행 결과였기 때문이다.

### 축 ④ **지금 고치지 않을 것**을 정하는 것이 리뷰의 결론이다

chia7712 가 계층 질문을 던졌다 — *"이 경우들을 전부 `AsyncKafkaConsumer` 층에서 다루는 건
고려해 봤나?"* Andrew 의 답이 이 PR 을 닫았다.

> *"One of the principles of the `AsyncKafkaConsumer` is that it tries to **eliminate sharing of
> state between the application and network threads**. Clearly, **it didn't quite manage that**,
> but the principle is still largely intact. […] I'd like to see a more comprehensive refactor,
> **but probably not right now**."*

원칙이 이미 깨져 있다고 **명시하고**, 이 PR 이 상황을 개선한다고 판정하고,
전면 리팩터링은 **미룬다.** 그리고 이틀 뒤 본인이 병합했다.

**"이건 아키텍처가 틀렸다" 가 자동으로 "이 PR 을 막는다" 가 되지 않는다.**
막을지 말지는 별개의 판단이고, **그 판단을 문장으로 남기는 것**이 시니어 리뷰의 산출물이다.

### 축 ⑤ 결함의 저자는 **창을 넓힌 설계 변경**이었다

이 장의 설계 리뷰 축은 "KIP 을 리뷰하는 법"이 아니었다. 본문이 말한다:

- 결함은 **KAFKA-18376**(비동기 poll 재설계)이 넣었다.
- **KIP-909**(비동기 부트스트랩 DNS 해석)는 코드를 건드리지 않았다.
- KIP-909 가 한 일은 **"사용 가능한 노드 없음" 창을 사실상 0에서 `bootstrapResolveTimeoutMs`
  까지 늘린 것**뿐이다.
- 그 순간 잠복 결함이 **눈에 보이는 busy loop** 가 됐다.

**KIP-909 를 리뷰한 사람 중 아무도 `FetchRequestManager` 를 보지 않았을 것이다.**
볼 이유가 없다. 그런데도 그 변경이 결함을 깨웠다.

> **타이밍 가정 위에 서 있던 코드는, 그 타이밍을 넓힌 무관한 변경에 의해 깨어난다.**
> 설계 리뷰에서 물어야 할 것은 *"이 설계가 옳은가"* 만이 아니라
> **"이 변경이 넓히는 창(window) 위에 누가 서 있는가"** 다.

이 문장은 교재에 이미 두 번 나왔다. **2장** — `open-in-view=true` 가 커넥션을 쥔 창을
요청 전체로 넓혔다. **5장** — 아무도 모르던 제약 하나가 읽기 경로에서 15~18배를 벌고
있었다. 셋 다 **아무도 그 창의 폭을 자기 변경의 일부로 보지 않았다.**
