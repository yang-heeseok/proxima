## 4.1 왜 남겼고, 왜 4장인가

**강등된 이유**는 하나뿐이다. PR당 인라인 리뷰 밀도 **0.74** — 0장 §0.7 측정 11개 저장소 중
아래에서 네 번째다. merge 650건 중 상당수가 메인테이너 자신의 커밋이고, 그건 리뷰를
거치지 않는다. **주교재로 쓰기에는 텍스트가 없다.**

**그럼에도 남긴 이유는 세 가지다.**

1. **영속성은 엔터프라이즈 Java 의 공통 지반이다.** Spring Data JPA 를 쓰는 순간 그 아래는
   Hibernate 다. 여기서 배우는 것은 proxima 지식이 아니라 **JVM 진영 대부분의 업무 코드가
   깔고 앉은 층**에 대한 지식이다. 목적 함수가 "일반 실무 전이력"으로 바뀌어도 이 장은
   살아남는다 — 바뀐 것은 순위지 자격이 아니다.
2. **정독 1건이 이미 완료되어 있고**(§4.5), 거기서 나온 교훈이 ORM 을 벗어나 일반화된다.
   §4.5(c)는 Hibernate 를 몰라도 성립하는 이야기다.
3. **밀도가 낮은 저장소를 읽는 법**의 표본이다. 실무에서 만나는 사내 저장소는 대개
   Kafka(7.8)가 아니라 Hibernate(0.74) 쪽에 가깝다. 텍스트가 희소할 때 어디를 파는지가
   오히려 더 자주 필요한 기술이다.

부수적으로 proxima 로드맵 4개 항목이 이 저장소 안에서 결정된다. **선정 근거는 아니고,
착지 지점이다.**

| 로드맵 | Hibernate 쪽 실체 |
| --- | --- |
| **T2** 인메모리 페이징 | `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory` — **그 경고 문자열의 출처가 이 코드베이스다** |
| **T3** 아무것도 안 하는 트랜잭션 | 프록시 초기화, dirty checking, `data class` 의 `equals` 가 lazy proxy 를 만나는 지점 |
| **T5** lost update | `@Version` optimistic locking, `LockModeType.PESSIMISTIC_WRITE` 가 실제로 뱉는 SQL |
| **T7** 쿼리 수를 세는 테스트 | `SessionFactory` 의 `Statistics` 계측 API |

## 4.2 판정 — 이 저장소에서 리뷰는 어디에 쌓이는가

0장 §0.9 의 학습목표 1번을 시연한 것이다. 전체 비교표는 0장 §0.7 에 있고, 여기서는
Hibernate 에 대한 판정만 남긴다.

밀도 0.74 라는 숫자가 뜻하는 것은 "읽을 게 없다"가 아니라 **"극단적으로 몰려 있다"** 이다.
0장 §0.3 의 집중도 — PR 88개 중 4개가 리뷰 텍스트의 34% — 가 바로 이 저장소에서 측정된
값이다. 그래서 Hibernate 에서는 무작위 읽기가 특히 나쁘다.

판정에서 나오는 실행 규칙이 하나 더 있다. **PR 제목 대부분이 `HHH-` 로 시작한다.**
문제 진술과 결정은 Jira 티켓에 있고 GitHub PR 에는 구현 리뷰만 남는다. 따라서:

> **Hibernate 는 티켓 먼저, PR 나중.** `HHH-#####` 를 Jira 에서 읽고 나서 PR 을 연다.
> PR 만 읽으면 "무엇을 고쳤나"는 보이지만 **"왜 그것이 문제인가"가 통째로 빠진다.**

Jira 는 `hibernate.atlassian.net/browse/HHH-#####` 로 알고 있으나 **여기서 확인하지 않았다 —
미측정.** 실시간 논의가 Zulip 에 있다는 것도 마찬가지로 확인하지 않았다.

## 4.5 정독 ① — PR #6038

`https://github.com/hibernate/hibernate-orm/pull/6038`
HHH-15964 · reda-alaoui 제안, sebersole(Steve Ebersole, 프로젝트 리드) 리뷰 · 2023-01-26 → 03-01

### 읽기 전 예측 (여기서 멈추고 직접 답할 것)

> Hibernate 는 **컬렉션 페치가 있으면 SQL 에 `LIMIT`/`OFFSET` 을 붙일 수 없다.** 조인으로
> 부모 행이 자식 수만큼 복제되어 나오므로, N번째 *행*이 N번째 *엔티티*가 아니기 때문이다.
> 그래서 전부 읽어와 메모리에서 자른다 — 그것이 `HHH000104` 경고다.
>
> 1. 이 판정(`containsCollectionFetches`)은 무엇을 보고 내려야 하는가?
> 2. **`EntityGraph` 로 컬렉션 페치를 추가하면** 그 판정은 어떻게 되는가?
> 3. 메모리에서 자르는 코드에 리뷰어가 가장 먼저 볼 위험은 무엇인가?

### 디프와 리뷰에서 실제로 읽히는 것

**(a) 결함의 형태 — 판정의 입력이 부족했다.**
기존 판정은 SQM(질의 트리)만 봤다: `sqmStatement.containsCollectionFetches()`. 그런데
`EntityGraph` 는 질의 문자열 밖에서 페치를 추가한다. 그래서 리뷰 중 확정된 형태가 이것이다.

```java
final boolean containsCollectionFetches =
        sqmStatement.containsCollectionFetches()
        || AppliedGraphs.containsCollectionFetches( getQueryOptions() );
```

**질의는 컬렉션 페치를 안 갖고 있는데 그래프가 갖고 있었고, 판정은 질의만 봤다.** 그래서
`LIMIT` 이 SQL 로 내려갔고 — 경고도 없이 — **틀린 결과가 나왔다.** 제목의 *Incorrect results*
가 그 뜻이다.

**일반화**: 어떤 조건을 판정하는 코드가 있고 그 조건에 기여하는 입력이 **둘 이상의 경로**로
들어올 때, 한 경로만 보는 판정은 조용히 틀린다. 그리고 조용히 틀리는 이유는 판정 자체가
"경고를 낼지 말지"를 결정하기 때문이다 — **판정이 틀리면 경고도 안 뜬다.**

**(b) 메모리 슬라이싱의 실물.** 리뷰어의 `suggestion` 이 이 두 줄에 집중된다.

```java
if ( first > resultSize ) { ... }
return list.subList( first, toIndex > resultSize ? resultSize : toIndex );
```

**리뷰어의 주의는 경계 조건으로 갔다.** `subList` 는 범위를 벗어나면 예외를 던지므로,
`first`/`toIndex` 를 결과 크기로 clamp 하는 것이 이 코드의 실제 위험이다. 위 예측 3번의 답이다.

**(c) 이 PR 에서 가장 값진 30초.** sebersole 이 `AppliedGraphs` 에 성능 의견을 낸다.

> "For performance, it would be better to track this as attribute-nodes are added to the
> graph I would think." — 질의 때마다 그래프를 훑지 말고, 노드를 **추가할 때** 미리 계산해 두자.

기여자가 반박한다.

> "`AttributeNode` and `GraphImplementor` can be mutable. `AttributeNode` also holds a map of
> mutable `SubGraphImplementor`…"

**가변 객체 위에 파생 상태(derived state)를 캐시하면 무효화(invalidation) 문제가 생긴다.**
불린 하나를 미리 계산해 두면, 그 뒤로 그래프가 바뀔 때마다 그 불린이 거짓말을 한다.
프로젝트 리드가 낸 최적화 제안을, 기여자가 **정확성 논거로 되돌린 것**이다.

이 장에서 배울 것을 하나만 고르라면 이 교환이다. **성능 제안에 대한 올바른 반론은
"느려도 괜찮다"가 아니라 "그 최적화는 언제 틀리는가"다.** Hibernate 를 한 줄도 모르는
사람에게도 성립하고, 캐시·메모이제이션·인덱스 추가 논의에 그대로 적용된다.

**(d) 잡음의 비율.** 인라인 17개 중 `.*` 임포트 지적 1개, 보안 스캐너 봇의 로그 관련
경고 2개. **고밀도 PR 에서도 2할 가까이가 배울 것 없는 코멘트다** — 0장 §0.3 의 주장이
같은 PR 안에서도 성립한다.

**(e) 리뷰 형식.** sebersole 은 GitHub 의 `suggestion` 블록을 주력으로 쓴다. 산문으로
"이렇게 바꾸세요"가 아니라 **커밋 가능한 디프를 코멘트로 던진다.** 왕복이 한 번에 끝난다.
현업에서 내일부터 쓸 수 있는 습관이다.

### 착지

- `docs/reports/` T2 리포트의 *남는 위험* 에: **"`HHH000104` 경고는 컬렉션 페치를 SQM 에서
  판정한다. `EntityGraph`/`@NamedEntityGraph` 로 페치가 추가된 경로는 이 저장소에서
  측정하지 않았다 — 경고 없이 결과가 틀리는 사례가 Hibernate 본체에서 보고된 적 있다
  (HHH-15964)."**

  쿼리 수만 세면 (a)류 결함은 통과한다.

## 4.7 정식 용어 — 이 장에서 나온 것

이름이 전이되는 부분이다. 우회 설명 대신 이걸 쓴다.

| 한국어로 뭉개기 쉬운 것 | 정식 용어 |
| --- | --- |
| 조인 때문에 행이 뻥튀기되는 문제 | **cartesian product** / row multiplication |
| 다 읽어와서 잘라내는 페이징 | **in-memory pagination** (Hibernate: `HHH000104`) |
| 깊은 페이지에서 안 무너지는 페이징 | **keyset pagination** (= seek method), ↔ **offset pagination** |
| 목록 하나 읽는데 쿼리가 우수수 | **N+1 select problem** |
| 버전 컬럼으로 충돌 잡기 | **optimistic locking** (`@Version`) ↔ **pessimistic locking** |
| 미리 계산해 둔 값이 낡는 문제 | **cache invalidation** / stale derived state |
| 로딩을 미루는 가짜 객체 | **lazy proxy**, **proxy initialization** |
| 바뀐 필드 찾아서 UPDATE 만들기 | **dirty checking** |
| 질의를 트리로 바꾼 것 | **SQM** (Semantic Query Model, Hibernate 6+) |

## 4.8 남는 위험 · 미측정

- **정독은 #6038 한 건뿐이다.** 나머지 4건은 메타데이터만 실측했고 **내용은 읽지 않았다.**
  4.4 표의 "전이되는 기술" 열은 제목·규모·키워드에서 나온 **추정**이며, 읽고 나면 바뀔 수 있다.
- **4.5(a) 의 인과는 리뷰 코멘트와 제목에서 읽어낸 것**이고, Jira 티켓 HHH-15964 의 원문
  재현 절차는 확인하지 않았다. 그래서 착지 문장을 "보고된 적 있다"로 한정했다 —
  우리가 재현한 것이 아니다.
- **표본은 최신 500개다.** 지금 이 프로젝트는 방언 호환 작업이 상위를 점유하고 있어서,
  다음 달에 같은 스크립트를 돌리면 4.3 표는 완전히 달라진다. **4.3 은 스냅샷이고 4.4 는
  아니다** — 관련도 축은 시간에 덜 흔들린다.
- **Jira · Zulip 미측정.** 4.2 의 "티켓 먼저" 규칙은 PR 제목의 `HHH-` 접두어라는 실측
  근거 위에 서 있지만, 티켓 쪽에 실제로 얼마나 많은 논의가 있는지는 세지 않았다.
- **강등 판단이 틀릴 수 있는 지점.** 밀도 0.74 는 *최근 90일* 값이다. Hibernate 는 6.x
  전환기(2021년경)에 리뷰가 훨씬 촘촘했을 가능성이 있고 — #3695(81), #2558(53) 이 그
  흔적이다 — **과거 구간의 밀도는 측정하지 않았다.** 즉 이 저장소는 "리뷰가 없는 곳"이
  아니라 "리뷰가 과거에 몰려 있는 곳"일 수 있다. 그렇다면 4.4 의 앵커 중심 접근이
  옳고, 4.3 의 밀도 스크립트가 이 저장소에서만 잘 안 듣는 것이다.
