# 1장 — 애노테이션은 아무 일도 하지 않는다

**Proxy, 그리고 트랜잭션 경계가 소리 없이 사라지는 네 가지 방식**

> 대상: NestJS/TypeORM·FastAPI로 운영 경험은 있지만 Java/Kotlin은 처음인 사람
> 목표: `@Transactional`이 붙어 있는데도 트랜잭션이 안 걸리는 상황을 **직접 진단하고 고칠 수 있는 상태**까지
> 선행 지식: 없음. 필요한 용어는 2절에서, Proxy는 3절에서 전부 깝니다
>
> **개정 2026-08-11 — 함정 ①이 이 저장소에서 재현·수정·게이트까지 끝났습니다.**
> 5절과 9절은 이제 설명이 아니라 **실제 로그와 숫자**를 인용합니다.
> 출처: `docs/reports/R1-transaction-annotation-that-does-nothing.md`>
> **감사 2026-08-20** — `R7`·`R9`·`R12`·`R16`·`R18` 과 대조했습니다.
> **`R13`·`R14`·`R15`·`R17`·`R19` 는 읽지 않았습니다** — 이 장의 다른 문장을 반증하는지 미확인.

---

## 0. 이 장의 한 문장

> **Spring의 마법은 전부 "당신 객체를 다른 객체로 바꿔치기하는 것"이고,
> 이 장의 함정들은 전부 "그 바꿔치기가 어디까지 유효한가"를 착각해서 생깁니다.**

함정을 네 개 외우는 게 아니라, **하나의 구조가 여러 얼굴로 나타나는 것**으로 보이게 만드는 게 이 문서의 목적입니다.

---

## 1. 당신이 이미 알고 있는 것에서 출발

Java를 몰라도 됩니다. 같은 문제를 이미 다른 언어에서 겪어봤기 때문입니다.

### NestJS에서

```ts
@Controller('learners')
class LearnerController {
  @UseInterceptors(LoggingInterceptor)   // ← 이 라우트에만 걸린다
  @Get(':id')
  findOne(@Param('id') id: string) { ... }
}
```

**인터셉터는 언제 동작합니까?** HTTP 요청이 Nest의 파이프라인을 통과할 때만입니다. 다른 서비스가 `learnerController.findOne('3')`을 **코드로 직접 호출하면 인터셉터는 안 탑니다.** 그냥 평범한 메서드 호출이니까요.

### FastAPI에서

```python
@app.get("/learners/{id}")
def find_one(id: str, db = Depends(get_db)):
    ...
```

`Depends(get_db)`는 **FastAPI가 이 함수를 라우트로서 호출할 때만** 작동합니다. 당신이 `find_one("3")`이라고 직접 부르면 `db`는 채워지지 않습니다.

### 그래서 공통 규칙은

> **횡단 관심사(로깅·인증·트랜잭션)를 "경계"에 붙이는 모든 프레임워크는, 그 경계를 지나지 않는 호출에 대해 무력합니다.**

NestJS는 그 경계가 **HTTP 파이프라인**, FastAPI는 **라우트 진입점**입니다. 둘 다 "프레임워크가 부를 때"라는 조건이 눈에 보입니다.

**Spring의 경계는 눈에 보이지 않는 곳에 있습니다.** 그게 이 장 전체의 이야기입니다.

## 2. 어휘 — 원문 그대로 익히기

번역어로 외우면 문서·에러 메시지·스택 트레이스에서 못 알아봅니다. **원문을 기준으로** 익히십시오.

| 원문 용어 | 한글 표기 | TS/Nest에서 가장 가까운 것 | 한 줄 설명 |
|---|---|---|---|
| **Annotation** `@Transactional` | 애노테이션 | **Decorator** `@Injectable()` | 코드에 붙이는 표시. **스스로 실행되지 않음** ⁽¹⁾ |
| **Bean** | 빈 | **provider** | DI 컨테이너가 만들어 관리하는 객체 ⁽²⁾ |
| **ApplicationContext** | 애플리케이션 컨텍스트 | Nest의 **module + injector** | Bean들을 담고 있는 컨테이너 그 자체 ⁽²⁾ |
| **Interface** | 인터페이스 | `interface` | 거의 같음. 단 Java에서는 **런타임에도 존재** ⁽³⁾ |
| **`final`** | 파이널 | **TS에 없음** | **상속·재정의 금지** ⁽⁴⁾ |
| **`open`** (Kotlin 전용) | 오픈 | **TS에 없음** | `final`의 반대. "상속 허용" ⁽⁴⁾ |
| **Bytecode** | 바이트코드 | 트랜스파일된 `.js` | 컴파일 산출물. **JVM이 읽는 것** ⁽⁵⁾ |
| **JVM** (Java Virtual Machine) | 자바 가상 머신 | Node 런타임 | 바이트코드를 실행하는 엔진 ⁽⁵⁾ |
| **Proxy** | 프록시 | **`new Proxy(target, handler)`** | **이 문서의 주인공 → 3절 전체** |
| **AOP** (Aspect-Oriented Programming) | 관점 지향 프로그래밍 | 인터셉터/미들웨어의 사상 | 횡단 관심사를 본문에서 분리하는 방식 ⁽⁶⁾ |
| **Reflection** | 리플렉션 | `Object.keys()` + 타입 정보 | 실행 중에 클래스·메서드·애노테이션을 들여다보는 기능 ⁽⁷⁾ |
| **JPA** (Jakarta Persistence API) | — | (해당 없음 — **규격**) | ORM **명세**. 인터페이스 모음일 뿐 ⁽⁸⁾ |
| **Hibernate** | 하이버네이트 | **TypeORM** | JPA 규격의 **구현체**. 실제로 일하는 쪽 ⁽⁸⁾ |
| **Persistence Context** | 영속성 컨텍스트 | TypeORM `EntityManager`의 1차 캐시 | 트랜잭션 동안 엔티티를 담아두고 변경을 추적하는 곳 ⁽⁹⁾ |
| **Lazy loading** | 지연 로딩 | TypeORM lazy relations | 연관 데이터를 실제로 쓸 때까지 미룸 → 7절 |
| **Propagation** | 전파 | **TS에 없음** | 트랜잭션 안에서 트랜잭션을 부를 때의 규칙 → 8절 |
| **CGLIB** | 씨지립 | (해당 없음) | 런타임에 클래스를 만들어내는 라이브러리 → 3절 |

---

### ⁽¹⁾ Annotation — Decorator와 뭐가 같고 뭐가 다른가

**같은 점.** 둘 다 코드에 붙이는 **메타데이터 표시**입니다. 문법도 `@이름` 으로 똑같이 생겼습니다.

**결정적으로 다른 점.** TypeScript 데코레이터는 **실행되는 함수**입니다. `@Injectable()`은 클래스가 정의되는 시점에 진짜로 호출됩니다.

```ts
function Log(target: any) { console.log('데코레이터가 지금 실행됨!') }

@Log
class Foo {}          // ← 여기서 콘솔이 찍힌다
```

**Java/Kotlin 애노테이션은 함수가 아닙니다. 실행되지 않습니다.**

```kotlin
@Transactional
fun record() { ... }     // 아무 일도 일어나지 않는다
```

컴파일 결과(바이트코드)에 *"이 메서드에 `@Transactional`이라는 표시가 붙어 있다"* 는 정보가 **기록만** 됩니다. 마치 주석처럼요. 차이는 **주석과 달리 프로그램이 실행 중에 그 표시를 읽을 수 있다**는 것뿐입니다 (→ Reflection, 주석 7).

> **그래서 누군가는 그 표시를 읽고 실제 행동을 해야 합니다. 그 "누군가"가 Spring이고, 방법이 Proxy입니다.**
>
> **이 문서 제목이 뜻하는 바가 정확히 이것입니다.**

---

### ⁽²⁾ Bean과 ApplicationContext — NestJS의 DI와 거의 같다

NestJS에서 `@Injectable()` 클래스를 module에 등록하면, Nest가 **당신 대신 인스턴스를 만들어서** 필요한 곳에 넣어줍니다. 당신은 `new`를 쓰지 않습니다.

Spring도 똑같습니다. 용어만 다릅니다.

| NestJS | Spring |
|---|---|
| provider | **Bean** |
| module / injector | **ApplicationContext** |
| `@Injectable()` | `@Component`, `@Service`, `@Repository` |
| 생성자 주입 | 생성자 주입 (동일) |

**이 장에서 중요한 사실 하나:**

> ApplicationContext는 **앱이 기동될 때 Bean을 전부 만들어 등록해둡니다.** 그리고 등록하는 그 순간에 **원본 대신 Proxy를 넣을 기회가 있습니다.** 이게 3절의 핵심 타이밍입니다.

---

### ⁽³⁾ Interface — TS와 다른 한 가지

TypeScript의 `interface`는 **컴파일되면 사라집니다.** 타입 검사용이고 런타임에는 존재하지 않습니다.

Java의 `interface`는 **런타임에도 실재하는 타입**입니다. 그래서 실행 중에 "이 인터페이스를 구현한 객체를 지금 만들어라"가 가능합니다. 3절의 JDK Dynamic Proxy가 바로 그걸 합니다.

---

### ⁽⁴⁾ `final` / `open` — **이 장에서 가장 중요한 어휘**

TypeScript에는 **"이 클래스는 상속할 수 없다"는 문법이 없습니다.** TS/JS 클래스는 항상 상속 가능합니다. 그래서 이 개념은 새로 익혀야 합니다.

```java
// Java
class Foo { }          // 상속 가능  ← 기본값
final class Bar { }    // 상속 불가
```

```kotlin
// Kotlin
class Foo { }          // 상속 불가  ← 기본값 (!!)
open class Bar { }     // 상속 가능
```

**Java와 Kotlin의 기본값이 정반대입니다.**

메서드에도 붙습니다. `final` 메서드는 **자식 클래스가 재정의(override)할 수 없습니다.** Kotlin은 메서드도 기본이 `final`입니다.

**왜 Kotlin이 그렇게 정했나.** "상속은 그렇게 설계된 클래스에만 허용하고 나머지는 막아라"는 오래된 설계 조언이 있습니다. 상속은 부모의 내부 구현에 자식이 얽히게 만들어서, 부모를 고치면 자식이 조용히 깨지기 때문입니다. Kotlin은 그 조언을 **언어 기본값**으로 만들었습니다. **좋은 결정입니다.**

**그런데** Spring의 Proxy는 **상속으로 만들어집니다.** 좋은 결정과 좋은 결정이 정면으로 부딪히는 지점이고, 그게 6절의 함정입니다.

---

### ⁽⁵⁾ Bytecode와 JVM — 왜 이걸 알아야 하나

```
  .java / .kt  ──컴파일──▶  .class (bytecode)  ──실행──▶  JVM
   (사람이 쓴 것)              (JVM이 읽는 것)
```

TypeScript → `.js` → Node와 구조가 같습니다.

**여기서 알아야 할 단 하나:** 바이트코드는 **꼭 컴파일러가 만들 필요가 없습니다.** 형식만 맞으면 **프로그램이 실행 중에 직접 써낼 수도 있습니다.** JVM은 그걸 그냥 로드해서 실행합니다.

> **Spring과 Hibernate가 하는 일이 정확히 그것입니다. 앱이 기동되는 동안, 메모리 위에 새 클래스의 바이트코드를 만들어내서 JVM에 밀어 넣습니다.**

JS로 비유하면 `new Function(...)`이나 `eval`로 클래스를 만들어내는 것과 비슷합니다. 다만 Java 진영에서는 이게 **정식이고 일상적인 기법**입니다.

---

### ⁽⁶⁾ AOP — 이름만 무섭지, NestJS 인터셉터와 같은 생각

Aspect-Oriented Programming. 우리말로 "관점 지향"인데, **용어보다 문제의식이 중요합니다.**

로깅·인증·트랜잭션 같은 것은 **모든 메서드에 조금씩 필요한데 어느 메서드의 본업도 아닙니다.** 본문에 직접 쓰면 비즈니스 로직이 잡일에 파묻힙니다.

```kotlin
fun record(e: Event) {
    log.info("시작")              // 잡일
    val tx = db.begin()          // 잡일
    try {
        repo.save(...)           // ← 본업은 이 한 줄
        tx.commit()              // 잡일
    } catch (ex: Exception) {
        tx.rollback()            // 잡일
        throw ex
    }
}
```

이런 **횡단 관심사(cross-cutting concern)** 를 본문에서 떼어내 한 곳에 모으자는 것이 AOP입니다. NestJS 인터셉터, Express 미들웨어와 **같은 문제의식**입니다.

**다른 점은 "어떻게 끼워 넣느냐"입니다.**

| | 끼워 넣는 방법 | 적용되는 범위 |
|---|---|---|
| NestJS 인터셉터 | 프레임워크의 **요청 파이프라인** | HTTP 요청으로 들어온 것 |
| Spring AOP | **객체를 Proxy로 바꿔치기** | Proxy를 거쳐 들어온 호출 |

Spring의 방식이 더 강력합니다 — HTTP가 아니어도 걸리니까요. 대신 **"Proxy를 거쳤는가"라는 새로운 조건**이 생기고, 그 조건은 눈에 보이지 않습니다.

### ⁽⁷⁾ Reflection — 애노테이션을 읽을 수 있게 해주는 것

실행 중에 **"이 객체의 클래스는 무엇이고, 어떤 메서드가 있고, 어떤 애노테이션이 붙어 있는가"** 를 물어보는 기능입니다.

```kotlin
val method = MasteryService::class.java.getMethod("record", Event::class.java)
method.isAnnotationPresent(Transactional::class.java)   // true
```

주석 1에서 "애노테이션은 실행되지 않고 기록만 된다"고 했는데, **그 기록을 읽는 도구**가 Reflection입니다.

**Spring이 기동할 때 하는 일이 결국 이겁니다:** 모든 Bean을 Reflection으로 훑어서 `@Transactional`이 붙은 걸 찾고, 찾으면 Proxy로 감쌉니다.

### ⁽⁸⁾ JPA vs Hibernate — 규격과 구현

혼동하기 쉬운데 관계는 간단합니다.

- **JPA**는 **명세(specification)** 입니다. "ORM은 이런 인터페이스를 제공해야 한다"는 **약속 문서와 인터페이스 모음**일 뿐, 실제로 SQL을 만들지 않습니다.
- **Hibernate**는 그 약속을 실제로 **구현한 라이브러리**입니다. SQL을 만들고, 커넥션을 쓰고, 캐시를 관리합니다.

비유하면 **JPA는 "USB 규격", Hibernate는 "실제 USB 케이블"** 입니다.

```
당신 코드 ──▶ JPA 인터페이스 (@Entity, EntityManager) ──▶ Hibernate 구현 ──▶ JDBC ──▶ PostgreSQL
```

**왜 이 구분이 중요한가.** 지연 로딩 Proxy(7절)는 **JPA 규격에 없는 Hibernate의 구현 방식**입니다. 즉 "JPA를 배웠다"고 해서 알 수 있는 게 아니라, **Hibernate가 그렇게 만들었기 때문에** 생기는 현상입니다. 함정 대부분이 이 층에 있습니다.

---

### ⁽⁹⁾ Persistence Context — 영속성 컨텍스트

트랜잭션이 사는 동안, 조회하거나 저장한 엔티티를 **메모리에 담아두는 상자**입니다. TypeORM `EntityManager`의 1차 캐시와 역할이 같습니다.

두 가지 일을 합니다.

1. **동일성 보장** — 같은 id를 두 번 조회하면 **같은 객체**를 돌려줍니다 (DB에 두 번 안 감)
2. **변경 감지(dirty checking)** — 담아둔 객체의 필드를 바꾸면, 트랜잭션이 끝날 때 **`UPDATE`를 자동으로 만들어 보냅니다.** `save()`를 호출하지 않아도요

> **이 상자의 수명은 트랜잭션과 묶여 있습니다.** 그래서 "트랜잭션이 어디서 시작해서 어디서 끝나는가"는 데이터 정합성만의 문제가 아니라 **이 캐시가 언제 살아있는가**의 문제이기도 합니다. 지연 로딩이 트랜잭션 밖에서 터지는 이유가 여기 있습니다.

## 3. Proxy — 이 문서의 주인공

여기를 이해하면 나머지 절은 전부 따라옵니다. 천천히 갑니다.

### 3.1 Proxy란 무엇인가

**대리인**입니다. 겉보기에는 본인과 구별되지 않고, 안에서는 본인에게 일을 넘깁니다.

성립 조건이 딱 둘입니다.

1. **겉보기가 같아야 한다** — 상대가 차이를 몰라야 한다 (= 같은 타입)
2. **진짜에게 위임한다** — 본업은 본인이 한다

그리고 **대리인이기 때문에 생기는 이득**이 하나 있습니다: **넘기기 전과 후에 뭔가를 할 수 있습니다.**

```
호출자 ──▶ [Proxy]  ── 앞에서 뭔가 한다 (BEGIN)
              │
              ├──▶ 실물 객체.메서드()
              │
           ── 뒤에서 뭔가 한다 (COMMIT / ROLLBACK)
```

### 3.2 JavaScript에는 이미 문법으로 있습니다

**당신은 이미 이걸 압니다.** JS에 내장된 `Proxy`가 정확히 그것입니다.

```js
const realService = {
  record(e) { console.log('  실제 저장:', e) }
}

const proxied = new Proxy(realService, {
  get(target, prop) {
    const original = target[prop]
    if (typeof original !== 'function') return original
    return (...args) => {
      console.log('BEGIN')                    // ← 앞
      try {
        const result = original.apply(target, args)
        console.log('COMMIT')                 // ← 뒤
        return result
      } catch (e) {
        console.log('ROLLBACK')
        throw e
      }
    }
  }
})

proxied.record('시도1')
// BEGIN
//   실제 저장: 시도1
// COMMIT
```

**Spring의 `@Transactional`이 하는 일이 이것과 똑같습니다.** 개념적으로 새로운 것은 하나도 없습니다.

### 3.3 그런데 Java에는 이 문법이 없습니다

JS는 동적 언어라서 **프로퍼티 접근 자체를 런타임에 가로챌 수 있습니다.** 그래서 `new Proxy()` 한 줄이면 끝납니다.

Java/Kotlin은 정적 타입 언어이고, **메서드 호출이 컴파일 시점에 결정됩니다.** "이 객체의 모든 메서드 호출을 가로채라"는 스위치가 언어에 없습니다.

**그래서 Java 진영은 무식하지만 확실한 방법을 씁니다:**

> ### 실행 중에 클래스를 새로 만들어냅니다.

앱이 기동되는 동안, Spring은 메모리 위에 이런 클래스의 **바이트코드를 직접 써서** JVM에 로드합니다:

```java
// 이런 클래스를 Spring이 런타임에 생성한다 (개념적으로)
class MasteryService$$SpringCGLIB$$0 extends MasteryService {

    @Override
    public void record(Event e) {
        TransactionStatus tx = txManager.begin();      // 앞
        try {
            super.record(e);                           // ← 실물 호출
            txManager.commit(tx);                      // 뒤
        } catch (RuntimeException ex) {
            txManager.rollback(tx);
            throw ex;
        }
    }
}
```

그리고 **ApplicationContext에는 당신의 객체 대신 이 클래스의 인스턴스를 넣습니다.**

주입받는 쪽은 아무것도 모릅니다. 타입이 `MasteryService`니까요. 자식 클래스는 부모 타입으로 취급되므로 완벽하게 속습니다.

> **"왜 이렇게 복잡하냐"의 답:** 언어에 기능이 없어서, 라이브러리가 바이트코드를 직접 씁니다.

### 3.4 만드는 방법이 두 가지 있습니다

**같은 타입이어야 한다**는 조건을 만족시키는 길이 둘뿐입니다.

| | **JDK Dynamic Proxy** | **CGLIB** |
|---|---|---|
| 방법 | **인터페이스를 구현**한 객체를 만든다 | **클래스를 상속**한 객체를 만든다 |
| 전제 조건 | 인터페이스가 **있어야** 한다 | 클래스가 **상속 가능**해야 한다 (`final` 아님) |
| 출처 | Java 표준 라이브러리 | 외부 라이브러리 (Spring 안에 포함되어 있음) |
| **Spring Boot 기본값** | | **← 이쪽** |

**Spring Boot는 CGLIB(상속 방식)을 기본으로 씁니다.** 인터페이스가 없어도 되니까 더 편해서입니다.

**그리고 바로 그 선택이, `final`이 기본값인 Kotlin과 부딪힙니다.** (→ 6절)

### 3.5 Proxy이기 때문에 생기는 제약 — 이게 함정의 정체입니다

Proxy는 **진짜가 아니라 진짜를 감싼 별개의 객체**입니다. 여기서 나오는 제약을 정리하면, 이 장의 함정 목록이 그대로 나옵니다.

| # | 제약 | 왜 | 어디서 터지나 |
|---|---|---|---|
| **A** | **`this`는 Proxy가 아니다** | 실물 객체 안의 `this`는 자기 자신이지 껍데기가 아님 | **함정 ①** (5절) |
| **B** | **상속할 수 없으면 만들 수 없다** | CGLIB은 상속으로 만든다 | **함정 ②** (6절) |
| **C** | **Proxy는 진짜가 아니다** | 필드가 비어 있을 수 있다 | **함정 ③** (7절) |
| **D** | **재정의할 수 없는 메서드에는 못 건다** | `private`·`final` 메서드는 오버라이드 불가 | 보너스 (아래) |

**보너스 D를 짚고 갑니다.** Kotlin은 **메서드도 기본이 `final`** 입니다. `kotlin-spring` 플러그인이 클래스와 함께 메서드도 열어주지만, 원리를 알아두면 이런 상황이 이해됩니다:

```kotlin
@Service
open class Foo {
    @Transactional
    private fun bar() { ... }     // private → 오버라이드 불가 → 트랜잭션 안 걸림
}
```

**애노테이션은 붙어 있고, 클래스는 열려 있고, 그런데도 안 걸립니다.**

### 3.6 함정 ④는 성격이 다릅니다 — 미리 말해둡니다

A~C는 **Proxy가 없거나 불완전해서** 생기는 문제입니다.

**함정 ④(8절)는 정반대입니다. Proxy가 완벽하게 동작한 결과 생깁니다.** Proxy가 두 번 제대로 걸렸는데, 그 둘이 **하나의 물리 트랜잭션으로 합쳐지기** 때문에 생기는 문제입니다.

그래서 ④는 "고장"이 아니라 **"설계된 동작인데 직관과 다른 것"** 입니다. 8절에서 봅니다.

### 3.7 Proxy는 Spring만 쓰는 게 아닙니다 — Hibernate도 씁니다

**이게 함정 ③의 뿌리이고, 많은 사람이 놓치는 부분입니다.**

Hibernate는 지연 로딩(lazy loading)을 위해 **똑같은 기법**을 씁니다. `attempt.item`을 아직 DB에서 안 가져왔을 때, 그 자리를 채울 뭔가가 필요하니까 **`Item`을 상속한 껍데기**를 만들어 넣습니다.

```
같은 도구, 다른 목적:

  Spring AOP Proxy      메서드 앞뒤에 트랜잭션을 두르려고
  Hibernate Proxy       필드 값을 실제로 쓸 때까지 미루려고
```

**Hibernate Proxy의 결정적 성질:**

> **필드는 비어 있고, 값은 getter를 호출할 때 채워집니다.**

```kotlin
val item = attempt.item     // 실제 타입은 Item$HibernateProxy
item.name                   // getter 호출 → 이때 SELECT 발생 → 값 반환
                            // 하지만 Proxy 객체의 "필드" 자체는 여전히 비어 있음
```

**getter로 접근하면 정상, 필드로 직접 접근하면 `null`.** 이 차이가 7절에서 `equals`를 무너뜨립니다.

한 객체에 **두 겹**이 씌워질 수도 있습니다. Spring이 감싼 서비스가 Hibernate가 감싼 엔티티를 다루는 식으로요.

### 3.8 눈으로 확인하는 법 — 실무 1차 진단

이론이 아니라 **1초 만에 확인**할 수 있습니다.

```kotlin
println(masteryService.javaClass.name)
```

| 출력 | 의미 |
|---|---|
| 이름에 **`CGLIB`이 포함** | Proxy가 씌워져 있음. 트랜잭션이 걸릴 수 있는 상태 |
| **클래스 이름 그대로** | **Proxy가 없음. `@Transactional`은 아무 효과가 없습니다** |

> "애노테이션이 안 먹는다" 상황의 절반은 이 한 줄에서 끝납니다. 막히면 가장 먼저 하십시오.
> (접미사 문자열은 Spring 버전마다 다릅니다. `CGLIB` 포함 여부만 보십시오.)

## 4. 그래서 `@Transactional`은 이렇게 동작합니다

3절을 요약하면 이 그림입니다.

```
[기동 시]
  ApplicationContext가 Bean을 만든다
      │
      ├─ Reflection으로 @Transactional을 발견              (주석 7)
      ├─ CGLIB으로 MasteryService를 상속한 클래스를 생성    (3.3, 3.4)
      └─ 컨테이너에 원본 대신 그 인스턴스를 등록

[요청 시]
  호출자 ──▶ [Proxy] begin ──▶ 실물.record() ──▶ commit
```

**핵심은 이 한 줄입니다.**

> **Proxy는 "호출자와 객체 사이"에만 존재합니다. 객체 안으로 들어간 다음에는 없습니다.**

## 5. 함정 ① — `this`는 Proxy가 아니다 (제약 A)

### 상황

여러 건을 처리하는 메서드가 같은 클래스의 건별 메서드를 부릅니다. 아주 자연스러운 코드입니다.

```kotlin
@Service
class MasteryService(private val repo: MasteryRepository) {

    fun recordAll(events: List<Event>) {
        events.forEach { record(it) }        // ← 문제의 줄
    }

    @Transactional
    fun record(e: Event) {
        repo.save(masteryOf(e))
        repo.save(historyOf(e))
    }
}
```

의도: `record` 하나가 실패하면 그 건의 두 `save`는 통째로 취소된다.

### 실제로 일어나는 일

```
호출자 → [Proxy] → 실물.recordAll()
                       └─ this.record()   ← Proxy를 안 거침!
```

`record(it)`은 `this.record(it)`이고, **`this`는 실물 객체입니다.** 4절 마지막 문장 그대로입니다 — 객체 안에는 Proxy가 없습니다.

`@Transactional`은 읽히지 않고, 두 `save`는 각각 따로 커밋됩니다. `historyOf(e)`에서 실패하면 **`masteryOf(e)`는 이미 커밋되어 남습니다.**

### 왜 안 잡히는가

컴파일 통과, 기동 성공, 로그 깨끗, **정상 동작 시 결과 완전히 동일.** 차이는 **중간에 실패했을 때만** 드러납니다.

### 이 저장소에서 실제로 관측된 것 — `R1`

여기부터는 설명이 아니라 관측입니다. red 커밋 `21e7162` 에서 `./gradlew :api:test` 를 돌렸을 때 나온 그대로입니다.

```
AttemptRecordingAtomicityTest > a recording that fails on its second write leaves no
attempt behind() FAILED
    org.opentest4j.AssertionFailedError: an attempt was committed by a unit of work that
    failed. The attempt and the mastery it updates are one unit -- a learner whose history
    and whose state disagree is not reconciled by anything downstream
    ==> expected: <0> but was: <1>
```

| 세는 것 | red `21e7162` | green `9388743` |
|---|---:|---:|
| 실패한 작업 단위 뒤에 남은 `attempt` 행 | **1** (기대값 0) | **0** |
| 같은 상황의 `mastery` 행 | 0 | 0 |

**동시성 1, 데이터 3행.** 부하도 규모도 필요 없었습니다 — 부하와 규모로 드러나는 결함을 모아둔 저장소에서 이 하나만은 **"중간에 뭔가 실패하기만 하면"** 됩니다.

증상의 문장이 중요합니다. **학습자의 이력은 문제를 풀었다고 하고, 숙련도는 안 풀었다고 합니다.** 두 줄이 서로 다른 말을 하고, 그것을 나중에 맞춰줄 것은 아무 데도 없습니다.

그리고 실제로 택한 처방은 아래 §근본 조치와 같았습니다 — `self.record(…)`(대증요법)가 아니라 **경계를 자기 Bean 으로 옮기는 것**. 네 가지 선택지의 비용 비교는 `R1` §5 에 있습니다.

### 근본 조치

흔한 답은 "자기 자신을 주입받아 `self.record()`로 불러라"입니다. **작동하지만 대증요법입니다.** 다음 사람이 다시 `record()`라고 쓰면 조용히 원상복귀됩니다.

근본은 질문을 바꾸는 것입니다.

> **트랜잭션 경계는 "실패하면 통째로 없던 일이 되어야 하는 업무 단위"에 붙어야 합니다.
> 그리고 그 단위가 무엇인지 아는 것은 호출하는 쪽입니다.**

- `record` 하나가 독립된 업무 단위라면 → **별도 Bean으로 분리**해서 진짜 Proxy를 타게 한다
- 전체가 한 단위라면 → **`recordAll`에 경계를 붙인다**

**내부에서만 호출되는 메서드의 `@Transactional`은, 동작 여부를 떠나 설계상 의미가 없습니다.**

### 재발 — 그리고 게이트가 처음으로 값을 친 순간 (`R7`, 2026-08-12)

이 함정은 **세 리포트 뒤에 다시 나타났습니다.** T3와 아무 상관 없는 작업 안에서, **T3 리포트를 쓴 바로 그 사람의 손으로.**

T6(유일성 경쟁)에서 *"삽입을 별도 트랜잭션으로 격리"* 하는 전략을 썼는데, 격리가 안 됐습니다.

```
MasteryProvisioner.insertInNewTransaction(long, long) is called from
MasteryProvisioner.findOrCreateIsolatingTheInsert(long, long), inside its own class,
so the call does not reach the proxy and @Transactional has no effect
```

**`REQUIRES_NEW` 가 새 트랜잭션을 시작한 적이 없습니다.** 그래서 "격리한" 버전이 개선하려던 버전과 **똑같이 8건 중 7건 실패**했습니다.

발견 순서가 중요합니다. **숫자가 먼저 이상했고, 원인을 문장으로 지목한 것은 T3 때 쓴 ArchUnit 규칙이었습니다.**

> **세 리포트 전에 쓴 게이트가 오늘 들어온 결함을 잡았습니다.**
> 게이트는 보통 **논증으로** 정당화됩니다. 이번이 처음으로 **스스로 값을 친** 경우입니다.

그리고 더 중요한 통계가 있습니다.

> **자기호출은 이제 서로 다른 세 함정의 *처방 안에서* 나타났습니다** —
> T3(주제 그 자체), T5(재시도를 다른 Bean으로 옮기면서), T6(여기).
> **이 결함들은 독립적이지 않고, T3가 나머지가 기대고 서 있는 바닥입니다.**

이 장이 1장인 이유가 사후에 증명된 셈입니다. 뒤 장들의 처방은 결국 *"경계를 어디에 두는가"* 를 다시 묻고, **그때마다 이 함정이 다시 문을 두드립니다.**

## 6. 함정 ② — 상속할 수 없으면 Proxy가 안 생긴다 (제약 B)

### 상황

Kotlin으로 서비스를 씁니다. Java 예제와 글자 하나 다르지 않게 생겼습니다.

```kotlin
@Service
class MasteryService(private val repo: MasteryRepository) {
    @Transactional
    fun record(e: Event) { ... }
}
```

### 실제로 일어나는 일

3.4에서 본 대로 Spring Boot는 **CGLIB(상속)** 으로 Proxy를 만듭니다.
주석 4에서 본 대로 **Kotlin 클래스는 기본이 `final`(상속 금지)** 입니다.

**상속할 수 없으니 Proxy를 만들 수 없고, Proxy가 없으니 트랜잭션도 없습니다.**

### 왜 Kotlin에만 있는 함정인가

Java 클래스는 기본이 열려 있습니다. 그래서 **Java로 쓰인 모든 튜토리얼·블로그·책에서 이 문제는 존재하지 않습니다.** Kotlin으로 넘어온 사람만 밟고, 검색해도 잘 안 나옵니다 — 결과가 전부 Java라서요.

### 근본 조치

`kotlin-spring` 컴파일러 플러그인(allOpen)을 씁니다. `@Component`·`@Service`·`@Transactional` 등이 붙은 클래스를 **컴파일 시점에 자동으로 `open`으로** 바꿔줍니다.

```kotlin
plugins {
    kotlin("plugin.spring")     // 이 한 줄
}
```

**이 프로젝트에는 이미 들어가 있습니다. 그리고 들어가 있다는 것이 증명되어 있습니다.**

회귀 게이트를 만들면서 이 함정을 **일부러 심으려 했더니 Kotlin으로는 심을 수가 없었습니다.** 컴파일러 플러그인이 컴파일 시점에 클래스를 열어버려서, 규칙에 도착할 때는 이미 고쳐져 있었습니다. 그래서 심는 코드 두 개를 **Java로** 써야 했습니다 (`R1` §7).

> **함정을 재현할 수 없다는 사실 자체가, 방어가 살아 있다는 증거입니다.**
> 그리고 플러그인을 지우는 순간 Kotlin으로도 심어집니다.

### 실무 인사이트

**설정 한 줄이 빠지면 애플리케이션 전체의 트랜잭션이 조용히 무효가 되는** 종류의 의존성입니다. 그리고 **빠졌을 때 아무도 알려주지 않습니다.**

그래서 이건 리뷰가 아니라 **테스트로 잡아야 합니다.** 이 프로젝트는 회귀 게이트로 ArchUnit(코드 구조를 검사하는 테스트 도구)을 쓰고 있고, 게이트 커밋은 `4141a65` 입니다. 다섯 규칙 중 이 함정을 맡는 것이 `TRANSACTIONAL_CLASSES_CAN_BE_SUBCLASSED` 입니다.

> *"`@Transactional`이 붙은 클래스는 `final`이면 안 된다"* 를 테스트로 강제한다.
> 누가 플러그인을 지우면 그 순간 CI가 빨간불이 된다.

그리고 한 걸음 더 갔습니다. **다섯 규칙 전부가 심어둔 위반을 실제로 거절하는 것을 눈으로 확인했습니다** — `TransactionBoundaryRulesSelfTest`, 테스트 6개.

> 규칙을 **쓰는 것**과 그 규칙이 **거절할 수 있는 것**은 다른 주장입니다.
> 후자를 확인하지 않은 게이트는 초록이라는 사실 말고는 아무것도 증명하지 않습니다.

### 그리고 규칙도 틀립니다 — 거짓 양성 하나 (`R7` §3.5)

자기호출 규칙이 실제로 결함을 잡던 그 실행에서, **틀린 것도 하나 잡았습니다.**

```
MasteryCounter.incrementWithRetryInside(long, int) is called from
MasteryCounter.incrementWithRetryInside$default(...)
```

Kotlin은 **기본 인자가 있는 함수**를 컴파일할 때 실제 함수와 함께 `foo$default` 라는 합성 정적 브리지를 만들고, 그 브리지가 실제 메서드를 부릅니다. ArchUnit 눈에는 자기호출로 보입니다.

**자기호출이 아닙니다.** 브리지는 **프록시를 수신자로 받아** 그것을 통해 디스패치합니다.

확정한 방법이 이 저장소답습니다 — **읽어서가 아니라 재서.** 그 메서드를 동시성 아래에서 실제로 돌려보니 트랜잭션이 내내 정상 동작했습니다. 규칙은 `$default` 브리지를 제외하도록 고쳐졌습니다.

> **routinely 틀리는 규칙은 아무도 읽지 않는 규칙이 됩니다.**
> 게이트를 갖는 비용에는 **거짓 양성을 없애는 비용**이 포함됩니다. 그 비용을 안 내면
> 게이트는 몇 주 안에 `// TODO: 이 규칙 왜 이러는지 모르겠음` 과 함께 꺼집니다.

## 7. 함정 ③ — Proxy는 진짜가 아니다 (제약 C)

### 상황

Kotlin이니까 자연스럽게 `data class`를 씁니다. `equals`·`hashCode`·`toString`을 공짜로 주니까요.

```kotlin
@Entity
data class Attempt(          // ← 하지 말아야 할 것
    @Id val id: Long? = null,
    val learnerId: Long,
    val correct: Boolean,
)
```

> **`data class`란?** Kotlin이 생성자 프로퍼티를 기준으로 `equals`·`hashCode`·`toString`·`copy`를 자동 생성해주는 클래스입니다. DTO에는 훌륭합니다. **엔티티에는 재앙입니다.**

### 문제 (a) — `equals`가 같은 행을 다르다고 한다

Kotlin이 생성한 `equals`는 **필드를 직접 읽습니다.** getter를 거치지 않습니다.

그런데 3.7에서 본 대로 **Hibernate Proxy는 필드가 비어 있습니다.**

```
실물 Attempt(id=7)  ==  Attempt$HibernateProxy(id=7)   →   false
```

같은 DB 행인데 다르다고 나옵니다. `contains()`, `Set`, `distinct()`가 전부 조용히 틀립니다.

### 문제 (b) — `hashCode`가 시간에 따라 변한다

생성된 `hashCode`는 **모든 프로퍼티**를 씁니다. 그런데 `id`는 저장 전 `null`, 저장 후 값입니다.

```kotlin
val set = hashSetOf(attempt)   // id = null 로 해시 계산 → 버킷 A에 저장
repo.save(attempt)             // id = 8 배정 → 해시가 바뀜
set.contains(attempt)          // false! 버킷 B를 뒤지므로 못 찾음
```

**집합에 넣어둔 객체가, 저장했다는 이유만으로 사라집니다.**

### 근본 조치

`data class`를 쓰지 않고 `equals`/`hashCode`를 직접 씁니다. 원칙 셋:

1. **`equals`는 id가 배정된 경우에만 id로 비교**한다. `id`가 `null`이면 "같은 인스턴스일 때만 같다"로 처리한다
2. **타입 비교를 `javaClass`로 하지 않는다.** Proxy는 서브클래스라서 클래스가 다르게 나온다. Hibernate가 제공하는 유틸로 **껍데기를 벗겨** 실제 타입을 비교한다
3. **`hashCode`는 시간에 따라 변하지 않는 값**을 반환한다. 엔티티에서 이를 만족시키는 현실적 선택은 클래스 기준 상수다

> `hashCode`의 계약은 **"객체가 사는 동안 변하지 않는다"** 입니다. id가 나중에 배정되는 엔티티는 이 계약을 지키기가 구조적으로 어렵고, 그래서 상수를 쓰는 것이 타협이 아니라 정답에 가깝습니다.

## 8. 함정 ④ — Proxy는 잘 걸렸는데, 트랜잭션이 하나로 합쳐진다

3.6에서 예고한 대로, 이건 **고장이 아니라 설계된 동작**입니다.

### 먼저: Propagation(전파)

메서드 A(트랜잭션 중)가 메서드 B(`@Transactional`)를 부르면 어떻게 될까요? 이 규칙을 **Propagation**이라 하고, **기본값은 `REQUIRED`** 입니다.

> **`REQUIRED` = "새로 만든다"가 아니라 "있으면 거기에 참여한다"**

이름이 오해를 부릅니다. "트랜잭션이 필요하니, 없으면 만들고 **있으면 그거 쓴다**"는 뜻입니다.

**결과: 물리적인 DB 트랜잭션은 처음부터 끝까지 하나뿐입니다.**

### 상황

부수 작업은 실패해도 본 작업은 계속하고 싶습니다. 지극히 정상적인 요구입니다.

```kotlin
@Transactional
fun recordAttempt(e: Event) {
    repo.save(attemptOf(e))

    try {
        statsService.bumpCounter(e)          // 이 안에도 @Transactional
    } catch (ex: Exception) {
        log.warn("통계는 실패해도 괜찮다", ex)  // 삼키고 계속
    }

    repo.save(masteryOf(e))
}                                            // ← 여기서 예외가 터진다
```

### 실제로 일어나는 일

`bumpCounter`는 `REQUIRED`니까 **새 트랜잭션이 아니라 바깥 것에 참여**합니다. 여기서 예외가 나면 Spring은 곤란해집니다.

**"안쪽 것만 롤백"이라는 선택지가 데이터베이스에 없기 때문입니다.** DB 트랜잭션에는 savepoint 없이 부분 롤백이 없습니다. 이미 하나로 합쳐진 트랜잭션의 일부만 되돌릴 방법이 없습니다.

그래서 Spring이 할 수 있는 유일하게 안전한 행동은 **트랜잭션 전체에 "커밋 금지" 표식(rollback-only)을 찍는 것**입니다.

당신은 예외를 처리했다고 믿고 진행합니다. 그러나 커밋 시점에 Spring이 그 표식을 보고 거부합니다:

```
UnexpectedRollbackException: Transaction silently rolled back
because it has been marked as rollback-only
```

**결과: "실패해도 괜찮다"고 했던 통계 때문에 본 작업인 attempt와 mastery까지 전부 사라집니다.**
게다가 예외는 `catch` 블록이 아니라 **메서드가 끝나는 지점**에서 튀어나옵니다. 스택 트레이스만 보면 원인이 안 보입니다.

### 근본 조치

요령이 아니라 **질문에 먼저 답해야 합니다.**

> **"이 실패는 정말로 감내 가능한가?"**

- **감내 가능하다 →** **물리적으로 분리해야 합니다.** 같은 트랜잭션 안에 있으면서 "나만 실패해도 돼"는 성립하지 않습니다.
  - `REQUIRES_NEW`: 진짜 별도 트랜잭션
  - `NESTED`: savepoint를 써서 부분 롤백
- **감내 불가능하다 →** **삼키면 안 됩니다.** 예외를 그대로 전파시켜야 합니다.

### 이 함정만 재현되지 않았습니다 — 그리고 그 이유가 교훈입니다

T3 작업에서 ①은 재현됐는데 **④는 일부러 빼서 T6으로 넘겼습니다.** 이유가 실험 설계 이야기입니다.

처음에는 두 번째 쓰기를 **DB의 CHECK 제약**으로 실패시켰습니다. 예외를 가짜로 주입하는 것보다 진짜 DB가 거부하는 쪽이 정직하다고 봤기 때문입니다. 그런데 PostgreSQL은 제약 위반이 나면 **트랜잭션 전체를 abort** 시켜버려서, 그 뒤의 모든 읽기가 이 에러로 터졌습니다.

```
org.hibernate.AssertionFailure: Entry for instance of 'Mastery' has a null identifier
```

**트랜잭션 경계와 아무 상관 없는 에러입니다.** 한 실험 안에서 두 가지가 동시에 일어나고 있었고, 그대로 갔으면 **두 가지를 재고 숫자 하나를 보고할 뻔했습니다.**

> **실패를 무엇으로 만드느냐가 실험 설계입니다.**
> 더 "진짜 같은" 실패가 더 좋은 실패가 아닙니다.
> **재려는 것 하나만 실패시키는 실패가 좋은 실패입니다.**

그래서 실패를 애플리케이션 규칙으로 바꿔 T3를 깨끗하게 유지하고, PostgreSQL의 트랜잭션 abort 동작은 **그것만 다루는 T6**으로 보냈습니다. 이 문서의 ④ 설명은 그래서 아직 **설명입니다.**

### 그리고 여기서 다음 장이 시작됩니다

`REQUIRES_NEW`에는 **대가가 있습니다. 커넥션을 하나 더 씁니다.**

바깥 트랜잭션이 커넥션을 쥔 채로 안쪽이 또 하나를 요구하기 때문입니다. **요청 하나가 동시에 쥐는 커넥션이 2개**가 됩니다.

커넥션 풀 크기 공식에서 이 숫자를 `Cm`(한 스레드가 동시에 쥐는 최대 커넥션 수)이라 부릅니다.

```
풀 크기 = Tn × (Cm − 1) + 1
```

**`Cm`은 보통 아무도 모르는 숫자입니다.** 그리고 방금 본 것처럼 **④를 고치는 행동이 `Cm`을 1에서 2로 올립니다.**

> **④의 처방이 다음 장(커넥션 풀 고갈)의 원인이 됩니다.** 따로 배우는 두 주제가 아니라 하나의 트레이드오프입니다.

## 9. 왜 테스트가 이걸 못 잡는가

### 표준 관행이 함정이 된다

Spring 통합 테스트는 관례적으로 테스트 클래스에 `@Transactional`을 붙입니다. **테스트마다 트랜잭션을 열고 끝나면 롤백해 DB를 깨끗이 유지**하려는 목적입니다. 합리적이고, 대부분의 프로젝트가 이렇게 합니다.

**그런데 이걸 붙이는 순간, 테스트 하니스가 당신 코드 대신 롤백해줍니다.**

서비스의 트랜잭션이 롤백했든, 애초에 트랜잭션이 없었든, **테스트가 끝난 뒤의 DB 상태는 똑같이 깨끗합니다.** 검증한 것은 서비스가 아니라 테스트 하니스입니다.

### 더 정확히는 — 보는 자리가 틀렸다

테스트 클래스에 `@Transactional`을 붙이면 **테스트와 테스트 대상이 하나의 트랜잭션을 공유합니다.** 서비스의 쓰기가 테스트의 트랜잭션에 합류하고, 하니스가 끝에서 통째로 롤백합니다.

> **한 트랜잭션을 공유하는 테스트는 그 코드의 트랜잭션 경계를 관측할 수 없습니다.**
> 어서션을 더 써서 회복되는 문제가 아닙니다. **보는 자리 자체가 틀린 것입니다.**

그리고 그 테스트가 *실제로* 검증한 것이 무엇이었는지가 압권입니다. "실패한 뒤에 `mastery` 행이 없다"를 확인했는데, 그건 **그 행을 쓸 문장이 바로 실패한 문장이었기 때문**입니다.

> **"throw 다음 줄은 실행되지 않는다"를 검증한 것입니다.**
> 어느 언어에서나 참이고, 트랜잭션에 대해서는 한 마디도 하지 않습니다.

### 판별법 — 이것만 기억하면 됩니다

> **서비스에서 `@Transactional`을 완전히 지우고 같은 테스트를 돌려보십시오.**
> **여전히 초록이면, 그 테스트는 트랜잭션이 있는 세계와 없는 세계를 구분하지 못합니다.**
> **두 세계에서 같은 답을 내는 테스트는 아무것도 검증하지 않은 것입니다.**

트랜잭션 전용 기법이 아닙니다. **"이 테스트는 무엇을 검증하는가"가 의심스러울 때 쓰는 일반 원칙**입니다 — 검증 대상을 망가뜨렸는데 통과하면, 그 테스트는 그걸 검증하지 않습니다.

### 이 저장소에서 실제로 재본 것 — `R1`

위 판별법을 그대로 실행했습니다. 애노테이션을 지우고 두 테스트 클래스를 다시 돌린 결과입니다.

| red 커밋 `21e7162` 에서 | 애노테이션 있음 | 애노테이션 **삭제** |
|---|---|---|
| `AttemptRecordingServiceTest` | **초록** | **초록** |
| `AttemptRecordingAtomicityTest` | 빨강 | 빨강 |

**네 칸, 두 세계, 차이 없음.** 그 시점에 `@Transactional` 은 이 저장소의 어떤 테스트에도 관측 가능한 영향을 주지 않았습니다.

고친 다음 같은 표를 다시 그리면 이렇게 됩니다.

| | 애노테이션 있음 | 애노테이션 **삭제** |
|---|---|---|
| red `21e7162` | 빨강 | 빨강 — **구분 못 함** |
| green `9388743` | **초록** | **빨강** — **구분함** |

> **테스트를 증거로 만드는 성질은 하나뿐입니다: 검증 대상을 없앴을 때 빨개진다.**

두 커밋 사이에 **테스트 파일은 한 글자도 바뀌지 않았습니다.** 바뀐 것은 경계의 위치뿐입니다.

### 같은 원칙의 두 번째 적용 — "초록"이라는 주장 자체

`R1` 은 이 원칙을 두 번 썼습니다. 두 번째는 코드가 아니라 **주장**에 썼습니다.

리포트를 다 쓰고 푸시했더니 CI가 빨간불이었습니다. 원인은 `gradlew` 가 **실행 권한 없이 커밋된 것**이었고 — Gradle이 시작조차 못 했습니다 — 로컬에서 안 보인 이유는 작업 트리가 WSL2의 drvfs 마운트 위에 있어서 **git이 무엇을 기록했든 모든 파일이 `0777` 로 보이기 때문**이었습니다.

즉 커밋 메시지의 *"green, 27 tests"* 는 **이 기계, 이 캐시, 이 작업 트리에서만** 초록이었습니다. `clean test` 로는 안 잡힙니다 — `build/` 만 지우지 의존성 캐시도 추적 상태도 안 건드리니까요.

> **CI 빌드를 정직하게 로컬 재현하는 방법은 빈 `GRADLE_USER_HOME` 으로 새로 클론하는 것입니다.**
> 그보다 덜한 것은 전부 *코드를 쓴 그 기계*와 상태를 공유하고, **그 상태가 바로 검증 대상입니다.**

같은 질문의 두 번째 판이었습니다 — *초록이라는 사실이 무엇을 증명하는가.* 첫 번째는 테스트가 트랜잭션을 안 보고 있었다는 것이었고, 두 번째는 초록이 한 대의 기계에 대한 진술이었다는 것이었습니다.

## 10. 실무 체크리스트

| # | 질문 | 아니라면 |
|---|---|---|
| 1 | 이 `@Transactional` 메서드는 **바깥에서 호출**되는가? | 같은 클래스 내부 호출이면 **무효** → 경계를 재설계 |
| 2 | 이 클래스는 **상속 가능**한가? (Kotlin이면 플러그인 있는가) | 없으면 **Proxy 자체가 없음** |
| 3 | 그 메서드가 `private`이거나 `final`인가? | 맞으면 **재정의 불가 → 무효** |
| 4 | 엔티티가 `data class`인가? | 맞으면 `equals`/`hashCode` 직접 구현 |
| 5 | 트랜잭션 안에서 **예외를 삼키는** 곳이 있는가? | 있으면 "감내 가능한가"부터 답할 것 |
| 6 | 이 테스트는 **애노테이션을 지워도 초록**인가? | 그렇다면 그 테스트는 무효 |

**막혔을 때의 1차 진단:**

```kotlin
println(service.javaClass.name)     // CGLIB이 없으면 Proxy가 없는 것
```

## 11. 요약

| 함정 | 착각한 것 | Proxy 제약 | 결과 |
|---|---|---|---|
| ① self-invocation | Proxy가 객체 **안에서도** 유효할 것 | A | 애노테이션 무시 |
| ② `final` 클래스 | Proxy가 **항상 만들어질** 것 | B | Proxy 자체가 없음 |
| ③ `data class` 엔티티 | Proxy가 **실물과 똑같이** 굴 것 | C | `equals`가 거짓 |
| ④ `REQUIRED` 전파 | 안쪽이 **별도 트랜잭션**일 것 | — | 전체가 롤백됨 |

①②③은 **Proxy가 없거나 불완전해서** 생깁니다.
④는 **Proxy가 완벽하게 동작한 결과** 생깁니다.

> Spring은 "선언적으로 보이게" 만들기 위해 **Proxy라는 값을 치릅니다.**
> 그리고 그 값은 **언제나 '경계'라는 형태로 청구됩니다.**

## 부록 — 어디까지가 관측이고 어디부터가 설명인가

**개정 2026-08-11.** 이전 판은 *"네 가지 함정 전부 재현 안 됨"* 이었습니다. 더 이상 사실이 아니라서 다시 씁니다. 이 구분이 이 저장소의 명제이고, 이 부록이 낡은 채로 있으면 그 명제를 문서가 스스로 어깁니다.

### ① 재현 → 수정 → 게이트까지 끝난 것

**함정 ① self-invocation** 하나입니다.

| | |
|---|---|
| 리포트 | `docs/reports/R1-transaction-annotation-that-does-nothing.md` |
| 결함이 관측된 커밋 | `21e7162` |
| 관측되지 않는 커밋 | `9388743` |
| 돌아오면 빨개지는 게이트 | `4141a65` |
| 측정 환경 | `R1` 상단 블록 (여기 옮겨 적지 않습니다 — 숫자는 한 곳에만) |

5절과 9절의 로그·표는 전부 여기서 왔습니다.

### ② 구조적으로 막혀 있으나 **재현되지 않은** 것

ArchUnit 규칙이 있고, 그 규칙이 심어둔 위반을 거절하는 것까지 확인됐습니다. **그러나 결함이 실제로 일어나는 것을 본 적은 없습니다.**

| 이 문서의 | 규칙 | 상태 |
|---|---|---|
| 함정 ② `final` 클래스 | `TRANSACTIONAL_CLASSES_CAN_BE_SUBCLASSED` | 막힘. 재현 **안 됨** |
| 함정 ③ `data class` 엔티티 | `ENTITIES_ARE_NOT_DATA_CLASSES` | 막힘. 재현 **안 됨** |
| 3.5 보너스 D (`private`/`final` 메서드) | `TRANSACTIONAL_METHODS_CAN_BE_OVERRIDDEN` | 막힘. 재현 **안 됨** |
| — | `ENTITIES_CAN_BE_SUBCLASSED` | 막힘. 재현 **안 됨** |

> **막는 것과 재현하는 것은 다른 주장입니다.** 규칙은 *"이게 동작할 수 있는가"* 에 답하고
> *"이게 동작하는가"* 에는 답하지 않습니다. 경계를 **잘못된 쓰기 묶음 주위에** 정확히
> 둘러도 다섯 규칙을 전부 통과합니다.

### ③ 이 장을 떠난 것

**함정 ④의 rollback-only 사례**는 T3에서 빠져 **T6**으로 갔습니다. 이유는 8절에 적었습니다 — PostgreSQL의 트랜잭션 abort가 같이 딸려 와서, 한 실험에서 두 가지를 재게 되기 때문입니다.

> **개정 2026-08-20.** 이 자리에는 *"여기 쓰인 ④의 설명은 아직 설명입니다"* 라고 적혀
> 있었습니다. **더 이상 사실이 아닙니다.** `R7` 이 T6에서 정면으로 쟀고, 숫자가 이렇습니다.

| 8건의 동시 요청, 유니크 제약이 있는 상태 | 남은 행 | 실패 |
|---|---:|---:|
| 순진한 존재 확인 후 삽입 | 1 | **7** |
| **예외를 잡고 같은 트랜잭션에서 다시 읽기** | 1 | **7** |
| 예외를 잡고 **자기 트랜잭션에서** 다시 삽입 | 1 | **0** |
| `insert … on conflict do nothing` | 1 | **0** |

**두 번째 줄이 이 장 8절이 설명만 하던 그것입니다.** PostgreSQL이 제약 위반에 트랜잭션 전체를 abort 시키므로, 복구를 위한 읽기가 **아무것도 실행할 수 없는 트랜잭션 안에서** 돕니다.

> **`catch` 블록에는 도달하고, 거기서 할 수 있는 것이 없습니다.**

그리고 `R1` §9가 T3를 재다가 **우연히** 만나 T6으로 보낸 그것이, T6에서 **의도적으로** 측정됐습니다. 자세한 것은 5장입니다.

### ④ 알면서 남겨둔 것 (`R1` §8에서)

- **self-invocation 규칙은 ArchUnit이 정적으로 해석할 수 있는 호출만 봅니다.** 필드에 담긴 람다, 리플렉션, Kotlin `by` 위임을 통한 호출은 **미측정**입니다 — 규칙이 그것들을 보는지 확인하지 않았고, 심어보지도 않았습니다. **흔한 형태를 잡는 규칙이지 증명이 아닙니다.** 10절 체크리스트 1번의 한계이기도 합니다.
- **배치가 부분적으로 기록되는 것이 이제 문서화된 동작입니다.** 5절에서 "작업 단위는 배치가 아니라 한 건"을 택한 결과이고, **호출자는 어디까지 저장됐는지 통보받지 못합니다.** 고치려면 건별 결과를 보고하거나 배치를 단위로 삼아야 하는데, 그건 리팩터링이 아니라 요구사항입니다.
- **건별 경계가 배치 경계보다 처리량에서 얼마나 손해인지 미측정.** 한 건마다 트랜잭션 하나면 왕복이 늘어납니다. 그럴듯한 비용이 있고, 재지 않았습니다.
- **게이트는 정확히 두 대의 기계에서 돌았고 두 번째에서 실패한 적이 없습니다.** 초록 한 번은 다른 JDK 패치 레벨·컨테이너 런타임·파일시스템에서의 안정성에 대한 주장이 아닙니다.
- **결론을 깨뜨릴 수 있는 것**: Spring이 서브클래싱으로 프록시 만들기를 그만두거나, Spring Data 리포지터리 메서드가 자기 트랜잭션을 여는 것을 그만두는 것. 후자가 새어 나간 행을 *영속적으로* 만드는 부분이고, 그게 없으면 증상 자체가 달라집니다.

### 그래서

이전 판의 마지막 문장은 이랬습니다 — *"이 장은 전자이고, T3가 후자입니다."*

**이제 절반만 맞습니다.** 함정 ①은 후자가 됐고, ②③④는 여전히 전자입니다. 그리고 그 차이를 아는 것이 이 부록의 전부입니다.

> **설명을 읽고 아는 것과, 초록인 테스트를 눈으로 보고 아는 것은 다릅니다.**
> 그리고 9절이 가르치듯, **"초록"이 무엇에 대한 진술인지도 다시 물어야 합니다.**
