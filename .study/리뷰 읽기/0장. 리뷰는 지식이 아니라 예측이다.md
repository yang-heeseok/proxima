## 0.0 이 트랙은 `.study/` 교재와 다른 것이다

`.study/` 최상위에는 **교재**가 있다 — `1장 애노테이션은 아무 일도 하지 않는다.md` 처럼
번호가 붙은 장들이고, 기술 자체를 1차 원리부터 가르친다. **2026-08-20에 9장으로 완결됐다** — 로드맵 아홉 항목이 1~6장과 8장에, 문서에 대한 것이 7장에, 채점이 9장에 있다.

> **개정 2026-08-20.** 이 문장은 원래 *"로드맵 순서(T3 → T1 → …)를 따른다"* 였다.
> 실제 순서는 **T3 · T1 · T2 · T5 · T6 · T4 · 문서 · T9 · 채점** 이고, 7장과 9장은
> 로드맵 항목이 아니다. **거짓이라기보다 낡은 요약이었고, 낡은 채로 두면 그것이 곧
> 교재 7장이 다루는 부류가 된다.**

**그 번호 체계는 교재의 것이고, 이 트랙은 거기에 끼어들지 않는다.**

이 폴더(`리뷰 읽기/`)는 **다른 축**이다.

| | `.study/` 교재 | `.study/리뷰 읽기/` (이 트랙) |
| --- | --- | --- |
| 가르치는 것 | **무엇이 어떻게 동작하는가** | **남의 디프를 보고 무엇이 터질지 예측하는 법** |
| 재료 | 문서화된 동작 + 직접 재현 | 남의 공개 코드리뷰 |
| 끝나는 지점 | 함정을 진단하고 고칠 수 있다 | 처음 보는 코드베이스에서도 스스로 재료를 찾아낸다 |
| 관계 | — | **교재의 원료 공급처.** 여기서 읽은 것이 교재 장의 근거가 된다 |

교재가 끝나도 이 트랙은 끝나지 않는다. **교재는 목록이 유한하고, 이 트랙은 방법이라서다.**

## 0.1 이 폴더의 규칙

> **개정 2026-08-17. 이 절은 두 번 틀렸다.**
>
> 원문은 *"`.study/` 는 `.gitignore` 에 이미 등재되어 있다"* 로 시작했고, 아래 표의 **추적**
> 칸은 *"없음. `git status` 는 계속 깨끗하다"* 였다. **둘 다 더 이상 사실이 아니다.**
> PO의 지시로 `374b59c` 가 무시 규칙을 지웠고, 이 커밋이 폴더 전체를 커밋한다.
> **원문을 지우지 않고 여기 남긴다** — 지우면 이 절이 무엇을 잘못했는지가 같이 사라진다.

`.study/` 는 이제 **추적되고 발행된다.** 영어 규칙(저장소 문서는 영어)은 이 폴더에 대해
PO가 철회했고, 그것이 원래 무시 사유의 절반이었다. 나머지 절반 — *공개 저장소에서
`git add -A` 가 상시로 쓰인다* — 은 무시로 막던 것을 이제 **막지 않으며**, 그래서 이 폴더에
쓰는 모든 문장은 발행을 전제로 쓰인다.

그래도 이 폴더는 본문과 다른 규칙 위에 있다.

| | 저장소 본문 (`docs/`, `README.md`) | 이 폴더 (`.study/`) |
| --- | --- | --- |
| 언어 | 영어 | **한국어** + 영어 정식 용어 병기 |
| 독자 | 공개 | **공개.** 원래는 PO 본인이었다 |
| 추적 | git | **git.** 원래는 추적되지 않았다 |
| 목적 | 증거 | 학습 |

**목적 칸만 남았고, 그것이 이제 이 폴더를 가르는 유일한 축이다.** 본문은 무엇이 참인지를
증명하고, 여기는 무엇을 어떻게 배웠는지를 기록한다 — **틀렸던 것을 지우지 않는 방식으로.**
이 절 자신이 그 형식의 표본이다.

**단 하나, 증거 규칙은 그대로 가져온다.** 이 폴더의 모든 숫자는 언제 어떤 방법으로 얻었는지를
달고 다니고, 얻지 않은 숫자는 `미측정` 이라고 쓴다. 학습 노트라고 해서 대충 쓴 숫자를 허용하면,
이 저장소 본문에서 지키는 규율이 두 개의 기준을 갖게 된다. 기준이 둘이면 그건 기준이 아니다.

## 0.2 전제 — 리뷰는 지식이 아니라 예측이다

코드리뷰 능력은 *아는 것*이 아니라 **디프를 보고 무엇이 터질지 먼저 떠올리는 능력**이다.

이 구분이 학습 방법 전체를 결정한다. 지식이라면 읽으면 쌓인다. 예측 능력이라면 **읽기만
해서는 절대 늘지 않는다** — 예측하고, 답을 보고, 틀린 축을 발견하는 순환이 있어야 한다.
리뷰어의 지적을 읽고 "아 그렇구나" 하고 넘어간 것은 다음 디프에서 재현되지 않는다.
재현되는 것은 **내가 먼저 틀려본 축**뿐이다.

그래서 이 교재의 모든 장은 같은 형태를 갖는다: **읽기 전에 예측을 적고**, 그 다음에 리뷰를
편다. 예측을 적지 않고 읽은 PR 은 이 교재에서 읽은 것으로 치지 않는다.

## 0.3 왜 그냥 읽으면 실패하는가 — 측정된 근거

**측정 2026-08-10.** `GET /repos/hibernate/hibernate-orm/pulls/comments?per_page=100&sort=created&direction=desc`
5페이지 = 최신 인라인 리뷰 코멘트 500개를 받아 PR 별로 집계했다.

```
표본 500개 · 분포된 PR 88개
  #12765  65개    ┃ 상위 4개 PR = 170개
  #12376  41개    ┃ = 전체의 34%
  #12413  35개    ┃
  #12880  29개    ┃
  #12710  14개
  ... 나머지 84개 PR 이 330개를 나눠 가짐 (평균 3.9개)
```

**PR 88개 중 4개가 리뷰 텍스트의 3분의 1을 갖고 있다.** 나머지 84개는 PR 하나당 평균 3.9개 —
대부분 오타, 스타일, `nit:`, `LGTM` 이다. 무작위로 PR 을 열면 84/88 의 확률로 그쪽에 떨어진다.

정보가 없어서 ROI 가 낮은 것이 아니다. **신호가 소수의 PR 에 몰려 있는데 그 소수를 찾는
비용이 크기 때문**이다. 그러니 방법의 절반은 "무엇을 읽을까"가 아니라 **"무엇을 읽지 않을까"**다.

> **평평한 쪽이 예외다.** 결론("다시 재라")은 그대로지만, **기대값은 "집중돼 있다" 쪽**이다.
> 표본 넷으로 규칙을 만들지는 않는다.

## 0.4 정정 — `sort:comments-desc` 는 틀린 레버였다

이전에 "코멘트 많은 순으로 정렬하라"고 했다. **그 지표는 인라인 코드리뷰를 세지 않는다.**
GitHub 에는 서로 다른 두 개의 카운터가 있다.

| 필드 | 세는 것 | 어디에 보이나 |
| --- | --- | --- |
| `comments` | **대화(conversation) 코멘트** | PR 의 Conversation 탭 |
| `review_comments` | **인라인 코드리뷰 코멘트** | Files changed 의 코드 줄 옆 |

`sort:comments-desc` 는 앞의 것으로 정렬한다. 우리가 배우려는 건 뒤의 것이다.

**측정 2026-08-10, `GET /repos/hibernate/hibernate-orm/pulls/{n}`:**

| PR | `comments` | `review_comments` | 비고 |
| --- | ---: | ---: | --- |
| #9650 | 5 | **92** | 18.4배. 코멘트 정렬로는 **바닥에 묻힌다** |
| #3695 | 25 | 81 | |
| #2558 | 22 | 53 | |
| #10194 | 7 | 45 | 6.4배 |
| #6038 | 31 | **17** | **역전.** 대화가 많다고 리뷰가 많은 게 아니다 |

#9650 이 결정적이다. **인라인 리뷰 92개짜리 PR 이 대화 코멘트는 5개다.** 내가 준
정렬 기준으로는 이 PR 을 영원히 못 만난다. 그리고 #6038 은 반대 방향으로 어긋난다 —
두 지표는 비례하지 않고, 한쪽으로 다른 쪽을 대신할 수 없다.

덧붙여 **Search API 는 `sort=comments` 를 무시한다.** `&sort=comments&order=desc` 를 붙이든
`&advanced_search=true` 까지 붙이든 반환 순서가 동일했다(2026-08-10 확인). 웹 UI 의
`sort:comments-desc` 는 동작하는 것으로 알고 있으나 **여기서 확인하지 않았다 — 미측정.**
어느 쪽이든 세는 대상이 틀렸으므로 쓰지 않는다.

### `merged` 도 못 믿는다

같은 부류의 함정이 하나 더 있다. **`is:merged` 는 프로젝트의 병합 방식에 좌우된다.**

| 저장소 | merged/90d | closed/90d | 왜 |
| --- | ---: | ---: | --- |
| openjdk/jdk | **2** | **941** | Skara 봇이 integrate 하고 PR 은 close 한다 |
| spring-projects/spring-boot | 95 | 145 | 메인테이너가 직접 다시 써서 커밋하고 PR 은 close |

openjdk 를 `is:merged` 로 재면 **90일간 2건짜리 죽은 저장소**로 보인다. 실제로는 인라인
리뷰가 6,208개다. 규칙: **밀도를 잴 때는 `closed` 를 쓰고, 리뷰 코멘트 수와 반드시 교차
확인한다.** 한쪽만 보면 세 번 중 한 번은 틀린다 — 지금까지 이 함정을 openjdk, Spring Boot
두 곳에서 만났다.

**반대 표본도 확인해 뒀다(2026-08-20).** `apache/kafka` #23014 는 `merged_at` 이 채워져 있고
병합자가 **리뷰어 본인**(`AndrewJSchofield`)이다. **Kafka 에서는 `merged` 가 정상 동작한다.**
즉 이건 "GitHub 지표를 믿지 마라"가 아니라 **"저장소마다 거버넌스가 다르니 PR 하나를 열어
확인하라"** 다. 확인 비용은 API 호출 한 번이다.

## 0.5 방법 — 네 단계

### (1) 밀도로 거르기 · 기계가 한다

정렬 대신 **집계**한다. 인라인 리뷰 코멘트를 긁어와 PR 별로 세면, 그게 곧 "논쟁이 있었던
PR" 순위다.

```bash
REPO=hibernate/hibernate-orm      # 저장소만 바꿔 재사용
for p in 1 2 3 4 5; do
  curl -s "https://api.github.com/repos/$REPO/pulls/comments?per_page=100&sort=created&direction=desc&page=$p" \
    > "rc_$p.json"
done
python - <<'PY'
import json, glob, collections
c = collections.Counter(); when = {}
for f in sorted(glob.glob('rc_*.json')):
    for x in json.load(open(f, encoding='utf-8')):
        n = x['pull_request_url'].rsplit('/', 1)[-1]
        c[n] += 1; when.setdefault(n, x['created_at'][:10])
for n, k in c.most_common(15):
    print(f'#{n:>6}  inline={k:<4} {when[n]}  https://github.com/{__import__("os").environ.get("REPO","")}/pull/{n}')
PY
```

비인증 호출은 시간당 60회다. 5페이지 = 5회이므로 저장소 3개를 매주 돌려도 여유가 있다.
**이 한 스크립트가 이 교재에서 가장 오래 쓸 도구다.**

### (1-b) 그리고 축이 하나 빠져 있었다 — **줄당 코멘트** (2026-08-20 추가)

위 집계는 코멘트를 PR별로 셀 뿐 **디프 크기를 보지 않는다.** 1장에서 그 대가를 봤다.

| | 바뀐 줄 | 코멘트 | **줄당** |
| --- | ---: | ---: | ---: |
| `openjdk/jdk` #32282 — 밀도 1위 | +5,424 / −19 | 128 | **0.02** |
| `openjdk/jdk` #26461 — 실제로 읽은 것 | **+24 / −6** | **132** | **4.4** |

**200배다.** 그리고 이것이 방법론의 문제인 이유는 (3)단계 때문이다 — **디프를 먼저 보고
지적할 점 세 개를 적으려면 디프를 통독할 수 있어야 한다.** 5,424줄짜리 PR에서는 그 단계를
**아예 수행할 수 없고**, 수행하지 않은 읽기는 이 교재에서 읽은 것으로 치지 않는다(0.2).

> **밀도 축이 뽑는 것은 "리뷰가 많은 PR"이지 "읽을 수 있는 PR"이 아니다.**

그래서 상위 목록을 받은 뒤에 **한 단계가 더 붙는다** — 각 PR의 `additions + deletions` 를
확인하고, **줄당 코멘트가 높은 쪽**을 고른다.

```bash
PR=<n>
curl -s "https://api.github.com/repos/$REPO/pulls/$PR" > pr.json
python - <<'PY2'
import json
d = json.load(open('pr.json', encoding='utf-8'))
lines = d['additions'] + d['deletions']
comments = d['review_comments'] + d['comments']
print(f"#{d['number']}  {lines}줄  {comments}코멘트  →  {comments/max(lines,1):.2f}/줄")
PY2
```

**다만 이 지표는 표본 둘로 만든 것이다**(1장 §1.8). 큰 PR이 항상 못 읽을 것도 아니고
작은 PR이 항상 논쟁적인 것도 아니다. **밀도 축을 대체하는 것이 아니라 그 뒤에 붙는다.**

> **개정 2026-08-20 — 이 축은 뽑아주지 않고 걸러주기만 할 때가 있다.**
> `apache/kafka` 에서 상위 12개 PR 의 줄당 값은 **0.01 ~ 0.13** 이었다. openjdk #26461 의
> **4.4** 와 34배 차이이고, 0.13 과 0.08 사이에는 고를 근거가 될 만한 차이가 없다.
> **그런데도 유용했다** — 3,899줄짜리와 2,865줄짜리를 탈락시켰다.
> **선택 도구로 못 쓰이는 저장소에서도 배제 도구로는 쓰인다.** 두 용법 다 정상이다.
>
> **세 번째 표본(2026-08-21).** `apache/lucene` 의 최고값은 **0.09** 였다.
> **openjdk 의 4.4 가 예외다** — Kafka 0.13, Lucene 0.09. 이 축은 **대개 배제 도구**이고,
> *"밀도 1위를 제치고 이걸 읽어라"* 로 동작한 것은 지금까지 openjdk 한 번뿐이다.

### (2) 관련도로 거르기 · 사람이 한다

밀도만으로는 부족하다. 실제로 2026년 여름 Hibernate 의 고밀도 PR 상위권은 Altibase/Spanner
방언(dialect) 호환 작업이 차지하고 있었다 — 리뷰는 촘촘하지만 **우리 결함 목록과 무관하다.**

그래서 축이 두 개다. **밀도는 기계가, 관련도는 그 주에 훈련하는 축이 준다.** 관련도의
출처는 로드맵일 수도 있고(그때는 proxima 에 착지한다), 훈련 중인 일반 기술일 수도 있다 —
후자가 이 교재의 기본값이다.

```
repo:openjdk/jdk is:pr path:src/java.base/share/classes/java/util/concurrent
repo:apache/kafka is:pr in:title race condition
repo:quarkusio/quarkus is:pr in:title thread
repo:hibernate/hibernate-orm is:pr firstResult maxResults
```

두 축이 겹치는 PR 만 교재에 들어간다. 겹치는 게 매주 나오지는 않는다. **안 나오면 안 읽는
것이 맞다** — 채우려고 무관한 PR 을 읽는 순간 이 방법의 전제가 무너진다.

### 그리고 축이 하나 더 붙었다 — **커밋 수** (2026-08-21 추가)

관련도까지 통과한 후보가 여럿이면 **커밋 수가 가른다. 읽기 난이도가 아니라 오염도의
지표로 쓴다**((3-a)).

| 커밋 수 | 뜻 |
| ---: | --- |
| 1~2 | 아직 아무도 안 고쳤다. **head 를 그대로 읽어도 된다** |
| 5~15 | 리뷰 이전 SHA 가 뚜렷하게 특정된다. **(3-a)① 이 잘 듣는다** |
| 40+ | 리뷰가 코드 전체에 스며 있다. **읽을 수는 있지만 예측 훈련으로는 값이 낮다** |

3장에서 Simple64(#16245, **커밋 52개**)를 이 기준으로 뒤로 미루고 #16515(커밋 8개)를 골랐다.

### (3) 순서를 뒤집기 · 이것이 핵심이다

PR 을 열면 Conversation 이 먼저 보인다. **그것을 접고 Files changed 부터 연다.**

1. 디프만 보고 **지적할 점 3개를 적는다.** 확신이 없어도 적는다.
2. 각각에 대해 "왜 문제인가"를 한 줄로 쓴다.
3. 그 다음에 리뷰를 편다.
4. **맞춘 개수는 기록하지 않는다.** 기록하는 것은 딱 하나 —
   **리뷰어는 봤는데 내가 보지 않은 축.**

3번까지 하지 않고 4번으로 간 읽기는 이 교재에서 읽은 것으로 치지 않는다. 나머지 세 단계를
합친 것보다 이 단계의 효과가 크다. 이유는 0.2 에 있다.

### (3-a) **병합된 PR 에서는 이 단계가 오염된다** (2026-08-20 추가)

**GitHub 의 `Files changed` 는 언제나 최종 상태를 보여준다.** 병합된 PR 에서 그것을 보고
예측하면, 예측의 재료가 이미 **리뷰의 산출물**이다.

2장(`apache/kafka` #23014)에서 실제로 셌다. **리뷰어 코멘트 20개 중 6개(30%)는
그 결과가 내가 읽은 디프에 이미 반영돼 있었다** — 리뷰어가 제안한 변수명이 그 이름으로
들어 있었고, 리뷰어가 요구한 `final` 이 붙어 있었고, 리뷰어의 질문이 만든 **삭제**를 보고
*"리뷰어가 이 삭제를 문제 삼을 것"* 이라고 예측했다. **같은 줄, 화살표 반대.**

그리고 이 오염은 **한 방향으로만 작동해서 더 위험하다.** 리뷰가 고친 자리에는 흉터가
남는다 — 이상하게 긴 이름, 유난히 구체적인 주석, 방금 삭제된 헬퍼. 흉터가 예측을 그리로
끌어당기고, **적중률이 오르는 만큼 배운 것은 없다.**

> **그리고 "열린 PR 이면 괜찮다"는 틀렸다.** 이 표의 ①은 처음에 *"열린 PR 은 결론이 없으므로
> 오염이 없다"* 였다. **오염의 원인은 병합이 아니라 수정이다.** `Files changed` 는 언제나
> 현재 head 를 보여주므로, **리뷰를 받고 고쳐진 PR 은 열려 있어도 리뷰의 산출물**이다.
> 1장이 정독한 openjdk #26461 은 **지금도 열려 있고 커밋이 42개**다(2026-08-20 확인) —
> 13개월 동안 40번 넘게 고쳐졌다. **열림/닫힘은 오염과 무관하다.**

| 대책 | 방법 | 신뢰도 |
| --- | --- | --- |
| **① 리뷰 이전 트리를 본다** | 첫 인라인 코멘트의 `original_commit_id` 를 찾고, **그 SHA 까지의 디프**를 읽는다. 3장이 이 방법의 첫 실행이다 | **가장 좋다. 완전하지는 않다 — 아래** |
| ② 리뷰 전 PR 을 읽는다 | 커밋 1~2개에 인라인 코멘트 0개면 아직 아무도 안 고쳤다. **커밋 수로 판별한다** | 대체로 |
| ③ 못 하면 세어서 적는다 | 봉인 파일을 남기고, 채점표에 **어느 적중이 무효인지** 표시한다 | 오염을 없애지 못하고 드러내기만 한다 |

```bash
PR=<n>; REPO=<owner/repo>
# 첫 인라인 코멘트가 달린 커밋 = 리뷰어가 실제로 본 트리
curl -s "https://api.github.com/repos/$REPO/pulls/$PR/comments?per_page=100"   | python -c "import sys,json;d=sorted(json.load(sys.stdin),key=lambda x:x['created_at']);print(d[0]['original_commit_id'],d[0]['created_at'])"
# 그 SHA 까지의 디프만 읽는다 (PARENT = 첫 커밋의 부모)
curl -sL -H "Accept: application/vnd.github.v3.diff"   "https://api.github.com/repos/$REPO/compare/$PARENT...$SHA"
```

> **그런데 ①도 샌다 — 3장에서 발견했다.** 리뷰 이전 SHA 를 찾으려면 **커밋 목록을 봐야
> 하고**, 첫 리뷰 이후의 커밋 메시지는 **리뷰에 대한 응답**이다. 3장에서는 목록에
> `Revert "Support two-phase filters in MaxScoreBulkScorer bitset path"` 가 있어서,
> **리뷰가 무엇을 되돌리게 만들었는지가 그대로 보였다.**
>
> **완전 무오염은 불가능하다. 가능한 것은 누출을 가시화하는 것이다.**
> 디프 오염은 무엇이 리뷰 때문에 바뀌었는지 표시하지 않지만, **커밋 메시지 누출은 줄
> 단위로 셀 수 있다.** 3장의 누출은 정확히 두 줄이었고, 봉인 파일에 **"오염됨 —
> 적중으로 셀 수 없음"** 이라고 적은 뒤 예측했다. **그리고 그 예측은 그러고도 틀렸다**
> (되돌린 이유를 성능으로 찍었는데 실제로는 PR 범위 문제였다) — **오염이 항상 적중을
> 만들어 주지도 않는다.**

### (3-b) 예측에는 두 모드가 있다 (2026-08-20 추가)

| 모드 | 언제 | 예측 대상 |
| --- | --- | --- |
| **결함 발견형** | 제목이 기능 추가다 (openjdk #26461 *"Add no-argument `codePointCount`"*) | **무엇이 터질까** |
| **해결 검토형** | 티켓이 문제를 이미 서술한다 (kafka #23014 *"A more obvious busy loop"*) | **이 고침의 무엇이 걸릴까** |

JIRA 로 굴러가는 저장소(Kafka·Hibernate)는 제목과 본문이 결함을 완전히 서술하므로
**결함 발견형 예측이 성립하지 않는다.** 후퇴가 아니라 다른 훈련이다 — 현업에서 받는 PR 은
대개 티켓이 붙어 있고, **"문제는 안다, 이 해결이 옳은가"** 가 더 흔한 리뷰다.
**다만 어느 모드로 읽었는지 적지 않으면 장끼리 채점을 비교할 수 없다.**

### (3-c) 새 메서드가 보이면 **그 파일의 이웃을 읽는다** (2026-08-20 추가)

2장에서 나는 새로 추가된 `hasFetchablePartitions` 가 기존 `fetchablePartitions` 와 중복이라고
예측했다. **아무도 지적하지 않았고, 지적했으면 내가 틀렸을 것이다** — 형제 메서드 세 줄 위에
`// Since this is in the hot-path for fetching, we do this instead of using java.util.stream API`
가 있었다. **중복이 곧 최적화였다**(리스트를 할당하지 않으려고 존재한다).

> **디프는 추가된 줄을 보여주지, 그 줄이 복사해 온 줄을 보여주지 않는다.**

내가 그 주석을 못 읽은 이유는 단 하나 — **디프에 없었기 때문**이다.
**디프에서 새 메서드·새 상수·새 분기를 보면, 그 파일을 열어 이웃을 읽는다.** 한 번의 파일
읽기가 "코드 품질 반사신경"이 만들어 내는 오답 대부분을 없앤다.

### (4) 착지시키기 · 산출물이 없으면 읽지 않은 것이다

PR 하나를 읽을 때마다 **이 저장소에 남는 한 줄**을 만든다. 셋 중 하나면 된다.

- 리포트의 *남는 위험* 항목 한 줄
- ADR 의 "검토했으나 택하지 않음" 한 줄
- T7(쿼리 수를 세는 테스트)의 어서션 하나

착지 지점이 없는 읽기는 증발한다. 그리고 이건 이 저장소의 규칙과도 맞는다 —
**구현 여부를 증명하는 것은 산문이 아니라 테스트와 리포트다.**

  코드리뷰 교재가 아니라 **"기본값을 바꾸는 비용"의 교재**이고, T1 착수 시 별도로 다룬다.

대충 여섯 개 읽는 것보다 제대로 두 개가 낫다는 것이 이 교재의 전체 주장이다.

## 0.9 학습 목표

이 교재가 끝났을 때 달성되어야 하는 것. **개별 PR 에서 배운 지식이 아니다.**

1. **저장소 판정** — 처음 보는 저장소를 받았을 때 30분 안에 "여기서 리뷰는 어디에 쌓이는가"를
   판정한다. 근거는 별 수가 아니라 `pulls/comments` 밀도, merged:closed 비율, 거버넌스
   모델(단독 메인테이너 / 회사 소유 / Apache 재단).
2. **예측** — 디프를 보고 리뷰어가 지적할 축을 절반 이상 미리 떠올린다.
3. **어휘** — 지적할 것을 **정식 용어로 부른다.** 우회 설명은 그 대화 안에서만 유효하고
   밖으로 나가지 못한다. 이름이 전이되는 부분이다.
4. **성능 주장을 격자로 요구한다** (2026-08-21 추가) — 숫자 하나를 받으면 **"어느 축으로
   훑었나"** 를 묻는다. 한 점은 검증할 수 없고, **격자는 메커니즘이 예측하는 방향을 갖는다.**
   3장의 두 표본이 같은 요구의 두 형태다 — Lucene 은 결과 표의 축(밀도 1~30%),
   Kafka 는 하네스의 `@Param`(voter set 3·5) 이고, **후자가 재현 가능한 장치로 남는다.**

1번이 가장 오래 간다. 이 문서 0.3~0.4 절을 만든 절차가 그대로 1번의 절차다.

## 0.10 남는 위험 · 미측정

- **인라인 코멘트 수는 대리 지표다.** PR 본문의 리뷰 요약(review body)과 이슈 스레드 토론은
  빠진다. 저장소 간 상대 비교로만 쓰고 절대값으로 쓰지 않는다.
- **그리고 작성자의 답변도 같이 센다(2026-08-20 확인).** `apache/kafka` #23014 는 인라인
  29개 중 **9개(31%)가 작성자 본인의 답변**이었다. 결함은 아니다 — 그 답변들이 그 PR 에서
  가장 긴 설계 논증이었다. 다만 **"인라인 29개"를 "리뷰어가 29번 지적했다"로 읽으면 틀린다.**
- **`?since=` 는 `updated_at` 기준**이라 오래된 코멘트가 최근 수정되면 포함된다. 0.3 의
  집계는 `sort=created&direction=desc` 를 썼으므로 이 문제를 피했지만, 저장소 간 90일
  비교에 썼던 수치는 이 오차를 안고 있다.
- **dependents / Maven Central 사용처 수는 측정하지 않았다.** "얼마나 많은 코드가 이걸 물고
  있는가"의 가장 정직한 지표인데 API 로 나오지 않는다. 별 수와 fork:star 비율로 대신했고,
  그건 대체재이지 같은 것이 아니다.
- **웹 UI 의 `sort:comments-desc` 동작 여부 — 미측정.** 어느 쪽이든 세는 대상이 틀려서
  쓰지 않기로 했으므로 결론에 영향은 없다.
- **가장 큰 위험: OSS 리뷰와 제품 팀 리뷰는 목적 함수가 다르다.** OSS 는 하위 호환성과
  메인테이너 대역폭을 최적화하고, 제품 팀은 출시 속도를 최적화한다. 이것만 학습하면
  "기본값은 못 바꾼다", "이 API 는 영원히 남는다" 같은 제약을 제품 코드에 과잉 적용하게
  된다. **저장소를 어떻게 고르든 남는다. 없앨 수 없고, 알고 읽는 수밖에 없다.**
- **표본 편향.** 0.3 의 500개는 최신 코멘트다. 즉 "요즘 이 프로젝트가 무엇을 하고 있나"에
  좌우된다 — 실제로 지금은 방언 호환 작업이 상위를 점유하고 있다. 주제별로 읽으려면
  밀도가 아니라 (2)의 키워드 축에서 출발해야 한다.
