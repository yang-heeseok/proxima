> **작성** 2026-08-20 · **대상** `openjdk/jdk` · **축** 언어와 표준 라이브러리의 정확성
> **상태** 밀도 실측 완료, 정독 1건 완료(#26461). **앵커의 현재 상태는 [`상태.md`](./상태.md)** —

## 1.1 왜 1장인가

0장 §0.7의 선정 근거는 하나였다 — **리뷰 대상이 Java 그 자체다.** `java.util.concurrent`·컬렉션·`java.time` 을 만든 사람들이 그것을 리뷰한다.

그리고 다른 저장소에 없는 성질이 하나 더 있다.

> **여기서 병합되는 공개 API는 사실상 영원히 남습니다.**

교재 5장이 *"제약은 규칙이자 자료구조"* 였다면, 여기서는 **메서드 하나가 영구적인 계약**입니다. 그 사실이 리뷰의 내용을 통째로 바꿉니다 — 그리고 그게 이 장에서 배울 것의 절반입니다.

---

## 1.2 판정 — 이 저장소에서 리뷰는 어디에 쌓이는가

0장 §0.5(1) 스크립트, **측정 2026-08-20.** 최신 인라인 리뷰 코멘트 600개.

```
표본 600개 · 분포된 PR 98개

확장자:  .java 45%  ·  .cpp 31%  ·  .hpp 17%  ·  .ad 2%
```

> **절반 가까이가 HotSpot C++ 입니다.** 필터 없이 읽으면 **Java 저장소에서 C++ 리뷰를 읽게 됩니다.**

0장 §0.7이 예고한 필터가 필수인 이유이고, 걸고 나면 이렇게 됩니다.

```
.java 코멘트만 : 274개 (45%) · PR 48개
```

**2026-08-10 표본에서는 `.java` 가 41%였고 오늘은 45%입니다.** 열흘 간격의 두 표본이 비슷한 값을 냈으므로, **이 비율은 그날의 우연이 아니라 이 저장소의 성질입니다.**

### `merged` 는 여전히 못 믿습니다

0장 §0.4가 적어둔 그대로다. Skara 봇이 integrate 하고 PR 은 close 하므로 `is:merged` 로 재면 90일에 두 건짜리 죽은 저장소로 보인다. **`closed` 를 쓰고 리뷰 코멘트 수와 교차 확인한다.**

## 1.4 그런데 1위를 안 골랐습니다 — **줄당 코멘트**

0장 §0.5(3)은 **디프를 먼저 보고 지적할 점 세 개를 적으라**고 요구합니다. 그 단계가 가능하려면 **디프를 통독할 수 있어야** 합니다.

| | 바뀐 줄 | 코멘트(인라인+대화) | **줄당** |
| --- | ---: | ---: | ---: |
| #32282 (밀도 1위) | +5,424 / −19 | 128 | **0.02** |
| **#26461** | **+24 / −6** | **132** | **4.4** |

**200배 차이입니다.**

> **밀도 축이 뽑는 것은 "리뷰가 많은 PR"이지 "읽을 수 있는 PR"이 아닙니다.**
> 0장 §0.5의 방법에는 **세 번째 축이 필요했습니다 — 줄당 코멘트.**

30줄이 바뀌고 코멘트가 132개 붙었다는 것은 **논쟁이 코드에 있지 않다**는 뜻이고, 그게 이 저장소에서 배울 것의 전부입니다.

**0장 §0.5(1)에 이 축을 더해야 합니다.** 스크립트는 코멘트를 PR별로 세지만 **디프 크기를 보지 않습니다.**

## 1.5 정독 ① — PR #26461

`https://github.com/openjdk/jdk/pull/26461`
*Add no-argument `codePointCount` method to String* · `+24/−6`, 3파일 · 인라인 56 · 대화 76 · **열려 있음**

### 1.5.1 읽기 전 예측 (0장 §0.5(3))

**디프가 하는 일:** `String` 에 인자 없는 `codePointCount()` 를 추가한다. `codePointCount(0, length())` 와 같다.

세 개를 적었다.

| # | 예측 |
| --- | --- |
| **1** | *"메서드 하나가 그만한 값을 하나."* 공개 API는 영원히 남으므로 `codePointCount(0, length())` 가 그만큼 불편한지를 물을 것이다 |
| **2** | *"이미 있는 방법."* `codePoints().count()` 가 있는데 왜. 논점이 발견 가능성/성능으로 옮겨간다 |
| **3** | *"명세 문구."* 구현보다 javadoc 한 줄에 코멘트가 더 붙고, CSR 이야기가 나온다 |

### 1.5.2 채점

**3번 — 적중.** 첫 코멘트에 들어 있다.

> *"And yes, **every change to the spec needs a CSR**."*

그리고 그 CSR이 **몇 달짜리 실타래**가 됐다. 기여자에게 JBS 계정이 없어서 커밋터가 대신 올려야 했고, *"Sorry for taking a million years"* 라는 문장이 실제로 있다.

**1번 — 절반.** 값에 대한 의문은 있었지만 **형태가 달랐다.**

> *"The recommended process for proposing new APIs is to put the proposal to the OpenJDK **core-libs-dev mail alias**. Putting the effort into a PR **before there is some agreement on the value is premature**."*

나는 *"리뷰어가 값을 따질 것"* 이라고 예측했고, 실제로는 **"여기가 그 논의를 하는 장소가 아니다"** 였다.

**2번 — 빗나감.** `codePoints().count()` 는 아무도 꺼내지 않았다. 실제로 다퉈진 대안은 **`Character.codePointCount(CharSequence)` 대 `CharSequence.codePointCount()` — 둘 중 무엇이 정본(canonical)인가** 였다.

### 1.5.3 내가 보지 않은 축 — **이 칸이 이 노트의 전부다** (0장 §0.6)

**넷이다.**

---

#### ① 인터페이스에 `default` 메서드를 더하는 것은 **별개의, 훨씬 큰 결정**이다

이 PR은 `String` 만이 아니라 **`CharSequence` 에도** 추가하려 했고, **거기서 막혔다.**

> *"The addition to `CharSequence` will require **static analysis to check for conflicts with implementation**. It will also likely **impact the `CharBuffer` spec**."*
>
> *"`CharSequence` is **widely implemented** and additions to this interface have a **history of disruption in the eco system**."*

**컴파일은 됩니다.** `default` 메서드는 기존 구현체를 깨뜨리지 않게 설계된 기능이니까요. **그런데 이미 같은 이름의 메서드를 가진 구현체와 충돌합니다** — 시그니처가 다르면 오버로드 해석이 바뀌고, 같으면 의도치 않게 오버라이드가 됩니다.

그래서 **정적 분석을 돌려서 생태계 전체를 확인해야** 합니다.

> **나는 `String` 만 보고 있었고, PR이 실제로 멈춰 선 곳은 `CharSequence` 였습니다.**

교재 5장의 *"제약은 규칙이자 자료구조"* 와 같은 부류다 — **한 줄의 결정이 다른 층에 흔적을 남기고, 그 층이 이 저장소 밖에 있다.**

---

#### ② 장소와 절차가 리뷰의 **첫 내용**이다

내가 예측한 것은 전부 **코드와 명세에 대한 지적**이었다. 실제 첫 코멘트 셋은 이렇다.

| | 무엇을 요구했나 |
| --- | --- |
| 1 | **메일링 리스트에서 먼저 합의**를 얻어라. PR이 먼저인 것은 이르다 |
| 2 | **`java.base` 밖의 모듈 변경을 빼라.** 제안을 API에 집중시켜라 |
| 3 | 명세가 바뀌면 **CSR** 이 필요하다 |

**셋 다 코드에 대한 말이 아닙니다.** 하나는 장소, 하나는 범위, 하나는 절차입니다.

> **큰 조직의 리뷰에서 첫 왕복은 대개 "무엇이 틀렸나"가 아니라 "이게 여기서 할 일인가"입니다.**
> 그리고 그것은 관료주의가 아니라 **비용 구조**입니다 — 영구적인 API에 대한 합의는 PR 하나보다 넓은 곳에서 이뤄져야 합니다.

---

#### ③ **버그 있는 호출자**에 대해서도 메모리 안전을 지킨다

인라인에서 가장 놀란 지적이다. `StringBuilder` 구현에 대해:

> *"In **buggy user program** that use `StringBuilder` from more than one thread, we can have `value.length < count`, so we must perform this call **checked**."*

`StringBuilder` 는 **스레드 안전이 아니라고 문서에 적혀 있습니다.** 그런데도 여러 스레드에서 쓰면 내부 배열 길이와 논리적 길이가 어긋날 수 있고, 그 상태에서 체크 없는 접근을 하면 **JVM 수준의 잘못된 메모리 접근**이 됩니다.

> **계약을 어긴 것은 호출자인데, 그럼에도 플랫폼은 메모리 안전을 유지해야 합니다.**

애플리케이션 코드에서는 *"문서에 안 된다고 적혀 있다"* 가 답입니다. **플랫폼 코드에서는 답이 아닙니다.**

---

#### ④ 리뷰어의 제안이 **틀릴 수 있고**, 받는 쪽이 재봐야 한다

한 리뷰어가 루프가 읽기 어렵다며 다시 쓴 코드를 제안했다. `if` 안의 `i++` 를 빼고 `for (int i = 1; ...)` 로 시작하는 형태였다.

**기여자가 jshell에 넣어보고 틀린 결과를 보여줬다** — 첫 문자가 보충 문자(supplementary character)인 문자열에서 답이 어긋난다. `i` 가 1부터 시작하므로 **인덱스 0의 서로게이트 쌍을 건너뛴다.**

> **가독성 제안이 정확성을 깨뜨렸고, 그것을 잡은 것은 제안한 쪽이 아니라 받은 쪽이었습니다.**

**리뷰 읽기 4장(#6038)에서 본 것과 같은 형태입니다** — 거기서는 프로젝트 리드의 성능 최적화 제안을 기여자가 *가변 객체 위의 캐시 무효화* 논거로 되돌렸습니다.

> **두 저장소에서 같은 모양이 나왔습니다.**
> **리뷰어의 제안은 코드가 아니라 가설이고, 그것을 검증할 사람은 기여자입니다.**

## 1.7 정식 용어 — 이 장에서 나온 것

| 한국어로 뭉개기 쉬운 것 | 정식 용어 |
| --- | --- |
| 명세를 바꾸려면 거쳐야 하는 심사 | **CSR** (Compatibility & Specification Review) |
| OpenJDK 의 이슈 트래커 | **JBS** (JDK Bug System) |
| PR을 integrate 하고 닫는 봇 | **Skara** |
| 인터페이스에 나중에 추가하는 구현 있는 메서드 | **default method** |
| BMP 밖의 문자 (`U+10000` 이상) | **supplementary character** |
| 그것을 UTF-16으로 표현하는 두 단위 | **surrogate pair** — 그리고 짝 없는 것이 **unpaired surrogate** |
| 정식 형태 / 나머지는 그것을 부르는 것 | **canonical** |
| 정식 출시 전 단계 | **Preview** · **Incubator** |
| javadoc의 반환값 인라인 태그 | `{@return …}` |

## 1.8 남는 위험 · 미측정

- **정독은 #26461 한 건이다.** 1.6의 세 건은 메타데이터만 실측했고 **내용은 읽지 않았다.** 표의 "얻는 것" 열은 제목·규모·코멘트 비율에서 나온 **추정**이다.
- **#26461은 열려 있다.** 여기 적은 것은 **2026-08-20 시점의 스레드**이고, 결론이 무엇이 될지는 모른다. **병합될지조차 모른다** — 첫 코멘트가 *"PR이 이른 것"* 이라고 적고 있다.
- **표본 600개는 최신순이다.** 지금 이 프로젝트가 무엇을 하고 있느냐에 좌우된다 — 지금은 JEP 540(JSON API)과 Argon2가 상위를 점유하고 있다.
- **`.java` 45% 는 코멘트 기준이지 PR 기준이 아니다.** C++ 과 Java 를 함께 건드리는 PR이 어느 쪽으로 세어지는지는 이 집계가 구분하지 않는다.
- **③의 메모리 안전 이야기는 리뷰 코멘트를 읽은 것이고, 실제로 그런 크래시를 본 것이 아니다.** 지적한 사람의 설명을 옮긴 것이다.
- **줄당 코멘트(1.4)는 이번 한 장에서 유용했을 뿐, 일반 지표로 검증되지 않았다.** 큰 PR이 항상 못 읽을 것도 아니고, 작은 PR이 항상 논쟁적인 것도 아니다. **표본 둘로 만든 기준이다.**
  - **추가 2026-08-20 · 세 번째 표본이 나왔다.** `apache/kafka` 에서 상위 12개 PR 의 줄당 값은 **0.01 ~ 0.13** 이었다 — 여기 #26461 의 **4.4** 와 34배 차이이고, 상위권 안에서는 고를 근거가 되지 못했다. **그래도 3,899줄·2,865줄짜리를 탈락시켰다.** 즉 이 축은 **선택 도구로 못 쓰이는 저장소에서도 배제 도구로는 쓰인다**(0장 §0.5(1-b), 2장 §2.2).
- **이 장의 채점에도 오염이 있다. 확인했다.** 2장에서 발견한 문제다 — **`Files changed` 는 언제나 현재 head 를 보여주므로**, 이미 리뷰를 받고 수정된 PR 의 디프는 **리뷰의 산출물**이다. 그것을 보고 한 예측은 답을 보고 문제를 맞힌 것일 수 있다(0장 §0.5(3-a)).
  - **#26461 은 지금도 열려 있다**(2026-08-20 확인, `state: open`, 병합된 적 없음). 그래서 처음에 이 줄을 *"열려 있었으므로 오염이 없다"* 로 썼다. **틀렸다.** 같은 조회가 **커밋 42개, 2025-07-24 개설**을 함께 보여줬다 — **13개월 동안 40번 넘게 고쳐진 PR** 이다. **열림/닫힘은 오염과 무관하다.** 무관한 것을 근거로 무죄를 주장하려던 문장이었고, 그것도 **같은 API 응답 안에 반증이 들어 있는 채로** 그랬다.
  - 이 장의 예측 중 **어느 것이 오염됐는지는 세지 않았다. 미측정.** 세려면 첫 커밋 디프와 대조해야 한다.
