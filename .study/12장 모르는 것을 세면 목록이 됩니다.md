## 1. 당신이 이미 알고 있는 것에서 출발

### 1.1 TODO 주석을 전부 모으면

코드베이스의 `TODO` 를 전부 긁어모아 본 적이 있다면 압니다. 세 종류가 나옵니다.

| | |
|---|---|
| **진짜 할 일** | 하면 됩니다 |
| **여기서는 못 하는 일** | 다른 팀·다른 권한·다른 환경이 필요합니다 |
| **이미 무효인 것** | 그 코드가 사라졌거나, 질문이 성립하지 않게 됐습니다 |

**셋을 안 나누면 목록 전체가 부채처럼 보입니다.** 그리고 부채처럼 보이는 목록은 아무도 안 봅니다.

### 1.2 "모든 X는 위험하다"에서 X를 세어 본 적이 있습니까

리뷰에서 이런 문장을 씁니다 — *"이 변경은 이 서비스의 모든 캐시 사용처에 영향을 줍니다."*

맞는 말일 수 있습니다. **그런데 캐시 사용처가 몇 개인지 세어 봤습니까.**

0개일 수도 있습니다. 그러면 문장은 **참이고 아무 의미가 없습니다.** 이 장의 2번 발견이 정확히 그것입니다.

## 2. 어휘 — 원문 그대로 익히기

| 용어 | 원문 | 뜻 |
|---|---|---|
| 콜레이션 ⁽¹⁾ | collation | 문자열을 **어떤 순서로** 볼지 정하는 규칙. 정렬과 비교의 근거 |
| musl / glibc | | 두 개의 C 표준 라이브러리. **로케일 지원이 다릅니다** |
| ICU | International Components for Unicode | 별도의 콜레이션 구현. PostgreSQL이 선택지로 제공합니다 |
| 매니페스트 digest ⁽²⁾ | image digest | 컨테이너 이미지 내용의 해시. **태그와 달리 움직이지 않습니다** |
| 공허참 | vacuous truth | 주어가 공집합인 전칭 문장. 참이지만 아무것도 말하지 않습니다 |

### ⁽¹⁾ 콜레이션 — `C` 가 뜻하는 것

`en_US.utf8` 로 정렬하면 사람이 사전에서 기대하는 순서가 나옵니다 — 대소문자를 섞어서 같은 글자끼리 모읍니다.

`C` 로 정렬하면 **바이트 값 순서**입니다. 아스키에서 대문자가 소문자보다 앞이니 `Z` 가 `a` 보다 앞입니다.

**그리고 musl로 빌드된 PostgreSQL은 `en_US.utf8` 이라고 선언해놓고도 바이트 정렬을 합니다.** 로케일 데이터가 없으니까요. 에러가 아니라 **조용한 대체**입니다.

### ⁽²⁾ 태그와 digest

`postgres:16-alpine` 은 **태그**입니다. 사람이 붙이고, **옮길 수 있습니다.**

`postgres@sha256:57c72fd2…` 는 **digest**입니다. 내용의 해시라 다른 내용을 가리킬 수 없습니다.

> **환경 블록에 digest를 적어놓고 테스트가 태그로 컨테이너를 띄우면, 적힌 것과 도는 것이 갈립니다.** 3번 발견입니다.

## 4. 발견 하나 — 위험은 진짜인데 주어가 비어 있었습니다

`R9` 8절이 이렇게 적었습니다:

> *"이 저장소의 **모든 텍스트 `order by`** — 그리고 그것이 함의하는 프로덕션 동작 — 은 glibc 또는 ICU 콜레이션 배포에 대해 검증되지 않았다."*

**전칭 문장입니다. 그리고 아무도 그 집합을 세어보지 않았습니다.**

### 4.1 먼저 메커니즘을 확인했고, `R9` 가 말한 것보다 컸습니다

digest로 못을 박은 두 이미지 — musl과 glibc — 에서 같은 네 문자열:

| | 결과 |
|---|---|
| musl | `Apple, Banana, apple, cherry` |
| **glibc** | **`apple, Apple, Banana, cherry`** |

그리고 **통제군**: 같은 glibc 바이너리 안에서 `collate "C"` 를 명시하면 musl 결과가 **정확히 재현**됩니다.

> **이 통제군이 차이를 콜레이션에 귀속시킵니다.** 두 이미지는 PostgreSQL 버전도 다릅니다(16.14 대 16.15). 통제군이 없으면 *"버전 차이 아니냐"* 에 답할 수 없습니다.

규모:

| | |
|---|---:|
| 비교한 2자 아스키 쌍 | 4,465 |
| **순서가 뒤집힌 쌍** | **4,461 (99.91%)** |
| 순위가 바뀐 출력 가능 문자 | **95 중 90** |

**`R9` 는 문자열 네 개로 위험을 적었고, 메커니즘은 그보다 훨씬 큽니다.**

### 4.2 그런데 그 위험이 걸린 집합이 비어 있습니다

트리 전체를 세었습니다.

| 정렬 대상 | 콜레이션이 걸리나 |
|---|---|
| 추천 쿼리 ×2 — 난이도와 id | 아니오 (숫자) |
| `BaselineMigrationTest` — 테이블명·인덱스명 | 아니오 (PostgreSQL `name` 타입, 콜레이션이 `C` 로 고정) |
| 마이그레이션 테스트 — id, 적용 순번 | 아니오 (정수) |
| **`R9` 자신의 프로브 ×2** | **예** |

**varchar를 정렬하는 문장은 위험을 제기한 그 프로브 두 개가 전부입니다.**

그리고 스키마의 텍스트 컬럼 다섯 개 중 콜레이션에 따라 위치가 바뀌는 것은 **하나**뿐이고(`G1-2` 와 `G10-12` 처럼 생긴 학년대), **아무것도 그것을 순서대로 읽지 않습니다.**

> **메커니즘은 확대되고 정량화는 철회됩니다.** 이 저장소의 세 번째 자기 정정입니다.

### 4.3 그래서 이게 왜 중요한 교훈인가

*"모든 X가 위험하다"* 는 문장은 **두 부분**입니다 — 메커니즘과 **적용 범위**. 리뷰에서 이런 문장을 쓸 때 우리는 보통 메커니즘만 확인합니다.

**메커니즘이 맞아도 범위가 비어 있으면 그 문장은 아무것도 요구하지 않습니다.** 그리고 그 상태로 남아 있으면, 나중에 범위가 채워졌을 때 아무도 다시 보지 않습니다.

원본 `R9` 는 **주석 한 줄과 날짜만** 받았습니다. 본문은 그대로입니다. 정정은 새 리포트에 있습니다.

## 5. 발견 둘 — 대안의 가격, 그리고 지속시간이 아닌 것

20만 행 정렬:

| 콜레이션 | 중앙값 | `C` 대비 | 편차 |
|---|---|---|---|
| `C` | **36.8 ms** | ×1.00 | 2.4% |
| `en_US.utf8` (glibc) | **98.1 ms** | **×2.66** | 5.9% |
| ICU | **55.8 ms** | ×1.51 | **18.1%** |

**ICU가 glibc보다 1.76배 빠릅니다** — 같은 언어적 순서를 주면서. *"정확하냐 빠르냐"* 는 축이 하나 모자랐습니다.

> ICU 편차가 18.1%로 10%를 넘어서 **비율을 "대략 1.5배"로만 인용**했습니다. 측정 규율이 편차를 밝히라고 요구하고, 밝히면 정밀도를 낮춰야 합니다.

### 5.1 더 큰 발견은 지속시간이 아니라 **계획**입니다

같은 행, 콜레이션만 다른 두 컬럼, 각각 B-tree 인덱스, 접두사 검색:

| | `en_US.utf8` | `C` |
|---|---|---|
| 계획 | **Seq Scan**, 199,900행을 필터로 폐기 | **Index Only Scan** |
| shared buffers | 1,471 | **5** (294×) |
| 실행시간 | 12.041 ms | **0.043 ms** (280×) |

**같은 SQL, 같은 인덱스, 콜레이션만 다릅니다.**

**왜 그런가.** 접두사 검색이 인덱스를 쓰려면 **범위 조건으로 바꿀 수 있어야** 합니다 — *"접두사 이상, 접두사+1 미만"*. 그 변환은 **인덱스의 순서가 바이트 순서일 때만** 성립합니다. 로케일 순서에서는 그 범위 안에 무엇이 들어올지 알 수 없습니다.

> 실무에서 접두사 검색용으로 `text_pattern_ops` 인덱스를 따로 만드는 이유가 이것입니다. 6장의 *"인덱스는 있는데 안 쓰인다"* 가 **한 층 아래에서** 다시 나온 것입니다 — 이번에는 컬럼 순서가 아니라 **컬럼의 콜레이션**이 원인입니다.

### 5.2 그리고 안 걸리는 것을 확인한 것이 이 절을 닫습니다

**유일성은 콜레이션과 무관합니다.** 대소문자만 다른 두 값이 양쪽 콜레이션에서 모두 삽입됩니다. 그래서 **5장의 유니크 제약과 `V3` 는 영향받지 않습니다.**

**경계를 정하는 음성 결과**입니다. 이것 없이는 *"콜레이션이 뭐든 바꿀 수 있다"* 가 남습니다.

## 6. 발견 셋 — 아무도 당기지 않는 digest

`docs/explanation/measurement-discipline.md` 는 이미지 digest를 적어놓고 그것이 *"행을 인용 가능하게 만드는 것"* 이라고 말합니다.

**그런데 테스트 설정은 태그를 못 박지 digest를 못 박지 않습니다.**

| | |
|---|---|
| 문서가 적어둔 digest | 2026-07-07 빌드, **PostgreSQL 16.14** |
| 태그가 실제로 가리키는 것 | 2026-08-13 빌드, **16.15** |
| 두 컨테이너에서 비교한 사실 | **12개** |
| 다른 것 | **3개** — 전부 같은 사실(버전 문자열)의 세 표현 |
| 마이그레이션·정렬 | **양쪽 동일** |
| `16.14` 라고 말하는 추적 파일 | **20개** |

### 6.1 그리고 CI와 로컬이 서로 다른 서버를 돌리고 있었습니다

`build.yml` 에는 **이미지 캐시가 없습니다.** GitHub 러너는 매번 새로 당깁니다.

**2026-08-13 이후 모든 러너는 16.15를 당겼고, 이 기계의 Docker 캐시는 7월 이미지를 들고 있었습니다.**

환경 블록은 **로컬 것**을 적고 있습니다.

### 6.2 이것이 `R17` 이 상상한 것보다 어려운 이유

`docs-consistency.yml` 은 **파일이 바뀐 날짜**와 `Updated` 날짜를 대조합니다. 그런데 여기서는:

- **파일이 하나도 안 바뀌었습니다**
- **모든 날짜가 맞습니다**
- **어떤 diff도 없습니다**

**문장을 거짓으로 만든 것이 커밋이 아니라 레지스트리입니다.** 날짜를 프록시로 쓰는 검사는 이것을 영원히 못 봅니다.

그리고 세어보면 하나 더 나옵니다: **digest는 `R1`~`R4` 에만 나오고, 2026-08-12 이후 어떤 리포트에도 없습니다.** 규율이 사흘 지켜지고 조용히 멈췄습니다.

### 6.3 그리고 이 절은 한 번 틀렸습니다 — 답이 이미 리포트 안에 있었습니다

> ## ⚠ 정정 2026-08-22 — **원문이 거짓이 된 것이 아니라 처음부터 틀렸고, 틀린 사람은 통합 세션입니다**
>
> 원문은 *"태그가 라운드 2가 도는 동안 또 움직였다"* 와 *"`postgres:16-alpine` 이름을
> 거쳐간 이미지가 셋"* 이라고 적었습니다. **둘 다 틀렸습니다.** 태그는 2026-08-13 에
> **한 번** 움직였고, B 와 C 는 **같은 이미지**를 돌렸습니다.
>
> ```
> Digest:    sha256:cf78e766…                    ← 태그가 가리키는 인덱스
> Manifests:
>   Name:      …@sha256:075f7ba6…
>   Platform:  linux/amd64                       ← 그 인덱스 안의 플랫폼 매니페스트
> ```
>
> **`075f7ba6` 은 `cf78e766` 과 다른 이미지가 아니라 그 안에 들어 있는 것입니다.**
>
> **그리고 이 정정에서 배울 것은 digest 가 아닙니다.** 위 출력은 제가 새로 돌려서 얻은 것이
> 아닙니다 — **`R27` 3절이 같은 명령의 출력을 전문으로 싣고 있습니다.** 인덱스 digest 와 그
> 안의 `linux/amd64` 매니페스트가 나란히 인쇄돼 있고, `R27` 의 표는 자기 수를 *"digest
> `postgres:16-alpine` resolves to, **linux/amd64**"* 라고 **레벨까지 붙여** 적었습니다.
>
> 통합 세션이 한 일은 이렇습니다: B 의 인계 문서에서 `cf78e766` 을, C 의 것에서 `075f7ba6`
> 을 보고, **두 수가 다르다는 것에서 두 이미지라는 결론으로 갔습니다.** 그리고 확인하려고
> `docker` 를 새로 조회했습니다. **30분 전에 자기가 병합한 리포트를 열어보는 대신에.**
>
> **이것은 이 저장소가 이미 이름을 붙여둔 실패입니다.** `R19` 가 센 것 — 나중 작업이 앞선
> 문서를 반증하는데 아무도 앞선 문서를 안 읽는 것. 여기서는 방향이 반대라 더 나쁩니다:
> **앞선 문서가 이미 옳았고, 새 "발견" 이 그것을 덮었습니다.**
>
> 원문을 지우지 않습니다. 아래는 정정한 본문입니다.

**digest 는 한 개의 수가 아닙니다.**

멀티 아키텍처 이미지에서 태그는 **인덱스**를 가리키고, 인덱스는 플랫폼별 매니페스트 목록을 가집니다.

| 무엇을 물었나 | 답 |
|---|---|
| `docker images --digests` / `RepoDigests` | `sha256:cf78e766…` — **인덱스** |
| 인덱스 안의 linux/amd64 매니페스트 | `sha256:075f7ba6…` |

**둘 다 참이고, 같은 이미지이고, 다른 수입니다.** *"이 이미지의 digest"* 라는 질문에는 두 개의 참인 답이 있고, **어느 레벨인지 말하지 않으면 다음 사람이 두 이미지로 읽습니다.** 방금 실제로 그렇게 됐습니다.

> **6절의 요점이 한 겹 깊어집니다.** 태그를 digest 로 고정하면 *움직이는 것* 은 해결됩니다. 그런데 **적어놓은 digest 가 어느 레벨인지 말하지 않으면**, 고정한 그 수도 다음 사람에게 모호합니다. `measurement-discipline.md` 의 환경 블록은 `sha256:57c72fd2…` 를 적으면서 인덱스인지 플랫폼 매니페스트인지 말하지 않습니다. **`R27` 은 자기 표에 레벨을 붙였고 환경 블록은 안 붙였습니다.**

**그리고 안전 확인 하나**: 7월 이미지와 지금 이미지의 alpine 과 musl 버전이 **동일**합니다(3.24.1 / 1.2.6-r2). 콜레이션 기반이 안 바뀌었으니 4·5절의 결론은 태그 이동에 영향받지 않습니다. **이 확인을 안 했으면 두 리포트가 서로 다른 바닥 위에 서 있을 뻔했습니다.**

**이 절이 이 장 전체에 대해 말하는 것.** 12장 4.3절은 *"메커니즘이 맞아도 범위를 세지 않으면 그 문장은 아무것도 요구하지 않는다"* 를 가르칩니다. 원문은 그 실수의 쌍둥이였습니다 — **세 수를 보고 세 이미지라고 세지 않고 결론냈습니다.** 12장이 가르치는 실수를 12장이 했고, 답은 이미 `R27` 안에 인쇄돼 있었습니다.

## 7. 이 슬라이스가 자기를 네 번 틀렸고, 네 번 다 스스로 잡았습니다

그중 하나가 이 교재에서 가장 배울 것이 많습니다.

**4.2의 표를 처음에는 `grep` 출력을 읽어서 옮겨 적었습니다.** 두 행을 하나로 합쳤고, 산문 한 줄을 절로 세었습니다. 그리고:

> **합계가 맞았습니다. 두 오류가 서로 상쇄됐기 때문입니다.**

**틀린 방법으로 맞는 답이 나온 것**이 가장 잡기 어려운 종류입니다. 검산으로도 안 잡힙니다 — 합이 맞으니까요. **방법을 다시 밟아야만** 나옵니다.

네 건 모두 **기계적으로 재유도해서** 잡혔습니다. 리뷰가 잡은 것도, 게이트가 잡은 것도 없습니다.

> **아는 모름을 센 목록은 값이 있고, 모르는 모름의 수는 아닙니다.** 이 구분을 흐리면 원장이 *"이제 다 안다"* 는 주장으로 읽힙니다. 세 군데에 그렇지 않다고 적혀 있습니다.

## 9. 실무 체크리스트

- [ ] *"안 쟀다"* 를 적을 때 **세 종류 중 무엇인지** 같이 적는가
- [ ] *"모든 X는 …"* 이라고 쓸 때 **X를 세어봤는가**
- [ ] 위험을 리포트에 남길 때 **메커니즘과 적용 범위를 따로** 확인했는가
- [ ] 컨테이너 이미지를 **태그로 고정하는가 digest로 고정하는가.** 문서에 digest를 적었다면 코드도 그것을 쓰는가
- [ ] CI와 로컬이 **같은 이미지**를 도는지 확인한 적이 있는가
- [ ] 정렬·비교가 걸린 컬럼의 **콜레이션이 무엇인지** 아는가. 컨테이너 베이스가 musl인지 glibc인지 아는가
- [ ] 접두사 검색이 인덱스를 쓰는가. **`EXPLAIN` 으로 확인**했는가
- [ ] 앞선 문서의 숫자를 인용할 때 **다시 계산해서 맞춰보는가**
- [ ] 합계가 맞았다고 **방법이 맞았다고 결론내지 않는가**
