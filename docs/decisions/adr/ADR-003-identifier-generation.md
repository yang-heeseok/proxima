# ADR-003 — Identifier generation stays `IDENTITY`, and here is the number that says when it should not

> **Created**: 2026-08-13
> **Updated**: 2026-08-13
> **Status**: Accepted
> **Closes**: `OPEN-3`

## Context

`BaseEntity` has used `GenerationType.IDENTITY` since the first entity, matching `V1`'s
`generated by default as identity`. It has been marked **provisional** in the source and open
in `docs/decisions/open.md` for three days, on the grounds that the trade was *worth measuring
rather than assuming*.

`open.md` then gave a reason not to measure it: **there is nothing to measure until a bulk
insert path exists.** That reason was wrong, and it was wrong in a way worth naming, because
it is how provisional choices become permanent ones. Whether `IDENTITY` prevents batching is a
property of the generator, the dialect, and the driver. It needs three entity classes and a
database. It never needed the application to grow a bulk path — and while everyone waited for
one, `R8` §8 and then `R9` §8 both recorded the question as unmeasured. **A deadline that
cannot arrive is not a deadline.**

### The measurement

`api/src/test/kotlin/net/gseek/proxima/db/IdentifierGenerationTest.kt`. Three arms differing
only in the generator, all with `hibernate.jdbc.batch_size = 50` — including the `IDENTITY`
arm, because *setting the batch size and having it do nothing* is the failure under
discussion. 1,000 rows per run, one warm-up discarded, 3 runs.

```
측정 환경 / Measurement environment
  Hardware   : Intel Core Ultra 7 258V, 8 cores / 8 threads, 31.5 GB RAM
  OS         : Windows 11 Home 10.0.26200 + WSL2 Ubuntu 24.04
  PostgreSQL : Testcontainers postgres:16-alpine -- server 16.14
  Framework  : Hibernate 7.4.1.Final via a standalone SessionFactory, Spring Boot 4.1.0
  Counter    : Hibernate Statistics.prepareStatementCount, asserted enabled before use
```

| arm | statements | ms (3 runs) | median | spread |
| --- | --- | --- | --- | --- |
| `IDENTITY` — what ships today | **1000** | 236, 290, 349 | **290** | 32% |
| `SEQUENCE`, `allocationSize = 1` | **1020** | 238, 262, 307 | **262** | 22% |
| `SEQUENCE`, `allocationSize = 50` | **40** | 27, 31, 43 | **31** | 37% |

The spreads are large and are stated rather than smoothed. The ratio `IDENTITY` ÷
`SEQUENCE(50)` came out **10.2×** on one full execution and **9.4×** on the next, so the
honest figure is *about ten times* and not a decimal. **The statement counts were identical
across every run and every execution** — 1000, 1020, 40 — which is why those are the numbers
the test asserts and the durations are only printed.

Three things follow, and only the first was expected.

1. **`IDENTITY` really does defeat batching.** 1,000 rows, 1,000 statements, with a batch size
   of 50 configured and ignored. Hibernate must execute each insert to read the generated key
   back, so there is nothing to accumulate.

2. **Switching to a sequence buys nothing on its own.** `allocationSize = 1` costs *more*
   statements than `IDENTITY` (1,020 against 1,000 — one `nextval` per row, plus one execution
   per batch) and its duration is indistinguishable from `IDENTITY` within the spread. The
   win does not come from the sequence. **It comes from the allocation size**, which is the
   part a migration is most likely to leave at its default.

3. **The hazard `open.md` recorded on 2026-08-10 reproduces exactly.** Five rows loaded with
   explicit ids and the sequence left at its start:

   ```
   first application insert, sequence NOT realigned : FAILED -- ERROR: duplicate key value
                                                      violates unique constraint "..._pkey"
   same insert after setval to max(id)              : INSERTED
   ```

   It was written down as a worry. It is now a measured fact with a test around it.

### What this measurement broke on the way in

**The commit that closed this decision, `8e5843a`, turned CI red**, and the way it did is worth
more than the inconvenience.

The four entity classes above were nested inside `IdentifierGenerationTest`, in
`net.gseek.proxima.db`. Its KDoc named the exact risk — *these must not join the application's
persistence unit* — and gave a mitigation: each arm builds a standalone `SessionFactory`, so
nothing measured here touches the application's schema.

That mitigation answers **who uses them.** The defect is **who finds them.**
`@SpringBootApplication` roots the entity scan at `net.gseek.proxima`, and test sources share
the classpath with main sources when tests run. Spring found all four, added them to the
application's persistence unit, and Hibernate refused to start any context:

```
Schema validation: missing table [t_open3_identity]
34 of 52 tests failed, across six classes -- none of them the one that changed
```

Local verification had been run as `--tests IdentifierGenerationTest`, which starts no Spring
context at all. **The scope of the check excluded everything the change could break.** `R8`
§3.1 says a test whose measurement scope is wrong passes and reassures; this is the same
mistake applied to the verification scope rather than the assertion scope, on the same day
that report's lesson was quoted in another commit message.

Fixed by moving the entities to `net.gseek.fixtures.open3`, outside the scan root.
`PersistenceUnitGateTest` now asserts the persistence unit's entity set exactly, so the next
occurrence fails with one sentence naming the cause instead of thirty-four schema-validation
stack traces in unrelated classes.

## Decision

**`IDENTITY` stays.** `OPEN-3` closes as *decided*, not as *expired*.

Ten times faster is a real number, and this application has nowhere to spend it. Every insert
path it has — `AttemptRecorder`, the mastery provisioning of `R6` and `R7` — persists **one
entity per transaction**, where `IDENTITY` costs one statement and `SEQUENCE(50)` costs one
statement plus a `nextval` every fiftieth row. The seed loader, the only thing here that
writes in bulk, uses `COPY` and bypasses Hibernate entirely.

Changing it now would mean a migration altering the identifier of all seven tables, a change
to what every id looks like, and the collision hazard above moving from a test into the
loader — **to make faster something this repository does not do.** This session has already
made that mistake once, reading a build file and nearly fixing entities that were never
`final`, and `R9` §5 rejected a second one on the same grounds.

### What flips this decision

Not a feeling that batching would be nice. One of these, observed:

| trigger | what changes |
| --- | --- |
| **Any insert path that persists more than one entity per transaction through Hibernate** — a bulk import, a fan-out write, a batch job | switch to `SEQUENCE` with `allocationSize` ≥ 50 |
| `IdentifierGenerationTest` going red on the `IDENTITY` arm | Hibernate has learned to batch identity inserts. The premise above is gone; re-derive it |

And when it does flip, three things travel together or the change is not done:

1. The sequence is **named** in the migration, not left to Hibernate's default.
2. The seed loader realigns **that** sequence after its `COPY`. Consequence 3 above is what
   happens otherwise, and it happens **only against a seeded database** — never against the
   empty one every test uses.
3. `allocationSize` is set deliberately. Consequence 2 above is what happens otherwise: a
   migration that looks like a performance fix and measures like nothing.

## Consequences

**What this buys.** The identifiers stay dense and sequential, `V1`'s DDL stays the plain
`generated by default as identity` that a reader expects, and the loader's `setval` on the
identity-owned sequence keeps working exactly as it does today. No change, and now a reason
for it.

**What this costs, and it is a real cost.** `hibernate.jdbc.batch_size` is inert in this
application, and will be for any code someone adds later, silently. Nothing warns. The first
person to write a bulk insert here will set the batch size, measure no improvement, and have
to find out why — **and the thing that tells them is this ADR plus a test that already
contains the number.** That is the trade: the cost is paid later by someone who will at least
find the answer written down.

It also means the ~10× is *unclaimed*, not *unavailable*. If a future report quotes this
repository's insert throughput, it must say that the configuration was chosen for a
single-row workload, or the number will read as a ceiling when it is a choice.

**What this rules out.** Adding a bulk insert path through Hibernate without revisiting this
document. The trigger table above is the condition, and `IdentifierGenerationTest` is what
notices.

## What was not measured

- **Batched inserts through the application's own entities.** The three arms use throwaway
  entities in a standalone `SessionFactory`, deliberately, so they cannot join the persistence
  unit and force their tables on every other test. The behaviour measured is Hibernate's, and
  the application's mapping is the same `IDENTITY` — but it was not the mapping on the bench.
- **`COPY` against batched Hibernate inserts.** The loader's path was not compared to
  `SEQUENCE(50)`; if a bulk path ever arrives, that comparison is the one that decides whether
  it should go through Hibernate at all.
- **The id gaps `allocationSize = 50` produces.** Up to 49 identifiers are burned on every
  restart. That is documented behaviour and was not observed here, and it is a real
  consideration for whoever flips this decision.
- **Whether any of this changes with `reWriteBatchedInserts=true`** on the PostgreSQL driver,
  which rewrites multi-row batches into a single statement. It is not set, it was not tried,
  and it could move the `SEQUENCE` numbers further.
